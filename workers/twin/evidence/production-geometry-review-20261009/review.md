## Findings (five implementation correctness issues; no style findings)

1. **P1: A successful rebuild deletes registered original source assets.** Batch.Save chooses the saved correction asset (1836–1849). KitBuild collects new meshes only when their paths remain under Kit/1F (3237–3238), so all six replacement meshes outside that folder are excluded. Cleanup deletes old receipt paths absent from that list (3248–3249). All six registered source paths are present in the current old receipt. Thus a successful rebuild will delete originals required for source evidence and for KitVerifyCorrections, which loads each original then immediately dereferences original.vertexCount (3363–3368). Preserve registered source assets explicitly, and include their continued existence in rebuild validation.

2. **P1: Registered source rejection can occur after shared-asset writes, without rollback.** KitBuild iterates batch.Save (3233), and each Save preflights only its own registration (1836–1845) before unregistered batches fill existing shared assets and mark them dirty (1847–1857). A later rejection, including the currently observed canopy mismatch, reaches catch that destroys only the new root (3240–3244); earlier shared mesh changes remain in assets and any old scene renderer using them. Preflight every registered batch and expected registration before any production mesh/material write, or stage all writes transactionally with restoration.

3. **P1: The verifier can report success while a registered owner was never regenerated.** KitVerifyCorrections checks only generated batches that have a registry match (3355–3358). Its sole completeness guard is comparisons.Count != 0 (3385), so a spec with one registered batch removed or skipped can return ACTUAL_SOURCE_REBUILD_CORRECTIONS_PASSED for the remaining subset. KitBuild replaces the entire old root, so the missing registered geometry is lost. Compare the generated set against the registry sources owned by the requested root, and reject missing, duplicated, or unexpected correction owners before reporting a pass. The current report contains six entries, so this is a contract gap rather than a claim that this run omitted an owner.

4. **P2: The transferred perimeter trim is outside the preservation contract.** The manifest removes 26 perimeter triangles from grid and installer creates a separate original trim renderer (ObservedCeilingInstall 100–114). Both ceiling registry publications refer only to the central relief filter (120–121); registry checks only that one companion's mesh and frame (63–73). The registry has no trim companion. Deleting, changing, or disabling the trim renderer still allows rebuilt grid to be accepted, leaving those 26 native perimeter triangles missing. Register and verify both required companions, including active/enabled rendering state and the material identity relevant to their preserved appearance.

5. **P2: Scene commit precedes registry and receipt commit, making metadata failure nonrecoverable by retry.** Installation saves the scene and sets committed=true (ObservedCeilingInstall 118–119), then publishes two rows independently and writes receipt (120–127). Failure in second publish or receipt write bypasses finally rollback (131–135), leaving a saved install and partial/missing metadata. The retry guard rejects the existing observed root or receipt (87). Use one registry publication containing both rows, and a recoverable commit journal or explicit metadata-repair path that validates existing saved scene/assets before completion. This is a failure-path issue; current receipt and six-row registry exist and their manifest hash matches.

Verification limits: no production rebuild executed and no fault injection performed. Findings 1–5 follow the live source control flow and current saved ownership/path data. The source-pixel/field accuracy limitation and canopy mismatch are existing measured boundaries, not inferred geometry improvements.
