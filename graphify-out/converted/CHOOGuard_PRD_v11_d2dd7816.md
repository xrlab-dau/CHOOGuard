# 00. 개정의 목적·정본·읽기 순서
## 00.1 무엇을 바꾸고 무엇을 유지하는가
이 문서는 PRD v10, 무료 우선 에셋 결정서, 문제·타겟·시간·시장·기술 비평 C01–C12를 통합한 v11 전체 개정본이다. 운영 시뮬레이션 중심, 작성자 주도, Unity PC, 실제 매뉴얼, 두 모드, 무료 우선 자산, 지원 범위의 정밀 물리 목표를 유지한다. 제품을 일반 대본 생성기·FPS·자유 건설 게임으로 바꾸지 않는다.
주요 변경은 기능 확대가 아니라 효용을 입증하는 방식과 낭비를 줄이는 기능이다. 반복 작성팀으로 타겟을 좁히고, 검수된 현장 묶음 재사용·변경 영향·부분 재실행·고객 양식 출력을 필수화한다. 기술 시제품, 사용자 효용 실증, 정량 모델 검증, 기관별 훈련 적용 승인, 사업 도입 판단을 서로 다른 의사결정으로 분리한다.
## 00.2 문서의 권한과 증거 상태

문서에 요구가 존재하는 것은 구현·검증·사업성의 증거가 아니다. 과거 내부 AAA 판정이나 자동 검사 횟수를 새로운 효용·정확도 승인으로 상속하지 않는다. BASIS-CRITIQUE
## 00.3 정본과 최소 문맥
서술 정본은 PRD.md, 원자 요구·인수시험의 정본은 contracts/requirements.json과 contracts/acceptance-tests.json이다. Word는 같은 서술의 읽기용 배포본이다. CHANGELOG.md는 변경 이유, CRITIQUE_TO_REQUIREMENTS.md는 C01–C12의 요구·시험 연결을 보여준다. history/는 읽기 기본값에서 제외한다.
개발 LLM은 START_HERE.md → agent-packets/EPxx.json → 현재 요구·시험 → 필요한 원문만 읽는다. EP00–EP11과 REQ-001–076은 식별자를 유지하고, 새 요구는 REQ-077부터 추가한다. 과거 DT/RS 계약과 새 계획을 병합해 모든 선행을 동시에 요구하지 않는다.
prepare는 읽기·설계, candidate는 자격 있는 입력과 쓰기경계 확인 후 구현, accept는 실행증거와 권한 있는 검수다. 문서의 단계는 담당자 선배정이나 저장소 쓰기 허가가 아니다.
# 01. 문제·가치 가설·제품 정의
## 01.1 클라이언트 요구와 최신 사용자 결정
사용자가 전달한 클라이언트 원문은 유관기관 비상대응 종합훈련 시나리오·대본의 자동 작성, 다양한 상황의 구조화, 대응 절차의 반복 점검·보완, 기관 공조·역할 검토, 작성 시간과 인력 절감을 기대한다. 원문 전문은 history/PRD_v10.md에 보존한다.
최신 사용자 결정은 시나리오 작성 담당자가 운영 시뮬레이션 게임처럼 대응안을 시험·비교·개선하는 경험으로 이를 구현하는 것이다. 대본부터 자동 완성하고 확인만 하는 순서로 핵심을 뒤집지 않는다.
## 01.2 해결할 문제
반복 합동훈련 작성팀은 기관별 업무·자원·보고·시설 조건을 바꿀 때, 후속 작업과 기관 간 인계·현장 이동의 충돌을 사전에 확인하고 선택 이유를 최종 대본까지 유지해야 한다. 이 변경 검토에 드는 부담과 잔존 오류를 줄이는 것이 목표다.
‘3D 맵이 없다’나 ‘AI가 없다’는 문제 정의가 아니다. 실제 고객에게 다음의 빈도·중요도를 최근 작성 사례로 확인한다: P1 변경 영향 추적, P2 자원·정보·공간상 실행 가능성, P3 근거·합의·서식 유지. 세 문제의 불편 규모는 아직 계측하지 않은 가설이다.
행정안전부의 상시훈련 목적, 코레일의 합동훈련, SR의 가상훈련 사례는 이 업무 영역의 존재를 뒷받침한다. 하지만 특정 팀의 작업시간·지불의사나 RTS의 우월성은 증명하지 않는다. DISC-01 DISC-03 DISC-04
## 01.3 제품 정의
CHOOGuard는 실제 철도 공간·기관별 매뉴얼·자원 및 물리 제약 아래에서 작성 담당자가 다기관 운영안을 RTS처럼 실행·분기·비교하고, 선택한 안을 근거가 연결된 종합훈련 시나리오·대본으로 전환하는 Unity PC 운영 실험 도구다.
운영 시뮬레이션이 본체, 맵은 판단을 실행하는 공간, 로그는 근거, 대본은 결과다. 기존 검토를 돕는 것이 목적이며 사용자가 더 오래 게임하는 것은 성과가 아니다.
## 01.4 검증할 가치와 실패할 수 있는 조건
가치 가설은 동등하거나 더 나은 품질의 대본까지 드는 총인시와 중대한 공조 모순을 줄인다는 것이다. 고객의 가장 큰 병목이 외부 회신 대기라면 그 지연을 시뮬레이터의 절감으로 주장하지 않는다. 단순 양식 편집만 문제라면 RTS의 추가 범위를 줄여 재설계할 수 있다. 핵심 운영 실험을 문장 생성으로 바꾸는 것은 별도 제품 결정이다.
첫 성공은 한 작성자가 A안의 문제를 근거로 설명하고 B안으로 수정해 차이를 확인한 뒤 고객 양식에 맞는 검토 가능한 대본을 만드는 것이다. 첫 기술 성공과 고객 총노력 절감은 서로 다른 증거다.
## 01.5 경쟁·대체재와 차별화 검증

공개 설명에 없다는 이유로 경쟁제품에 기능이 없다고 단정하지 않는다. 업체 속도 광고를 독립 생산성 수치로 사용하지 않는다. 데모·가격·현행 기능은 도입 조사 때 재확인한다. 훈련 기관·참가자·역 수를 고객 수나 매출로 환산하지 않는다. DISC-07 DISC-08 DISC-09 DISC-10

# 03. 타겟·권한·첫 실증의 진입 조건
## 03.1 첫 타겟과 핵심 사용 상황
첫 타겟은 같은 철도 현장 또는 재사용 가능한 현장 묶음에서 합동훈련을 반복 기획하고 기관별 업무와 대본을 통합하는 작성 책임자·실무팀이다. 나이·직급·급여를 가정한 가상 페르소나를 만들지 않는다.
핵심 사용 상황은 “참여기관·자원·보고·시설 조건이 변경됐을 때, 영향을 받는 업무를 확인하고 대안을 시험해서 관계기관이 검토할 수 있는 대본을 다시 완성한다”이다. 새 훈련 기획과 강평 개선 반영도 사용 유발 상황으로 조사한다.
## 03.2 사용자와 이해관계자

역할이 겹쳐도 독립 사람 수로 중복 집계하지 않는다. 실제 프로그램 사용자와 가상 소방·경찰·철도 인력은 별개다. 작성자의 가상 편집 권한은 모든 실제 기관의 지휘권이 아니다.
## 03.3 첫 실증 파트너의 진입 조건
허용된 최근 초안·최종 대본과 수정 의견, 적용 매뉴얼 판본 또는 제한 검수 경로, 해당 현장의 최소 연결·자원 정보, 사용할 제출 양식, 실제 작성자와 검수자의 참여가 있어야 고객 효용 실증을 시작한다. 개인정보·보안정보는 비식별화한다. 참여 의사·자료 협조·파일럿·구매 승인은 서로 다른 상태다.
자료가 없을 때 합성 두 기관 fixture로 코어·화면을 개발할 수 있지만 이를 고객 실증으로 보고하지 않는다. 기준 자료 없이 대규모 현장별 맞춤 제작을 시작하지 않는다. 필요한 입력은 pilot-intake.json에 존재·접근·담당·대체경로·소비단계를 기록한다.
## 03.4 범위와 제외
첫 제품 공간은 외부 도착 경계·현장 업무 공간·맞이방·승강장·선택 객실이다. 최초 실행은 두 기관·소수 팀의 지원–배정–수행–보고–인계 흐름으로 제한한다. 이후 인력·차량·사건을 늘린다. 기존 13개 root ID와 최종 확장 목표는 보존한다.
과거 16팀·대응인력64명·일반인120명·도로차량10대·열차1편성은 부하 시험 제안값으로만 유지하며 공식 편성·최초 필수 범위가 아니다. 운전자·승무원을 중복 계산하지 않는다.
VR/HMD/XR 개발·시험, FPS, 자유 건설·수익 경영·전투·공격 최적화·실제 설비 제어는 제외한다. 일반 승객·소비자 게임 시장·일회성 문구 수정 사용자는 초기 주 타겟이 아니다. 교육·연구 프로젝트의 개발을 구매계약 확보의 선행으로 막지 않는다.
# 04. 두 사용자 모드와 핵심 여정
## 04.1 공통 규칙
사용자 모드는 정확히 TUTORIAL과 RANDOM_OPERATIONS_LAB 두 개다. 편집·재생·기관별 정보 보기·물리 계산 프로파일은 모드가 아니라 공통 도구/설정이다. 두 모드는 같은 버전의 공간·권한·업무·자원·보행·물리·로그 코어를 사용한다. 힌트가 켜졌다고 차량이 빨라지거나 자원이 회복되지 않는다.
주 여정: 상황 선택 → 운영안 A 실행 → 병목·미충족 조건 확인 → 시점 저장/분기 → 운영안 B 실행 → 동일·변형 조건 비교 → 담당자 선택 → 대본 작성·검토 → 검토된 시나리오를 다시 실행.
## 04.2 TUTORIAL: 실제 훈련·매뉴얼 기반 교육

계산상 불가능, 검토된 필수 규칙, 허용된 지휘 재량, 권고, 미확인 조건을 분리한다. 훈련 목적상 잘못된 제안을 기록할 수 있어도 물리적으로 없는 자원을 만들어 실제 실행 성공처럼 표시하지 않는다. 허용 예외는 원문 근거·범위·행위자·사유·결과를 남긴다. 경고를 무시하는 편의 기능으로 매뉴얼 전체를 해제하지 않는다.

## 08.3 개정·영향분석
매뉴얼이 바뀌면 해당 규칙, 튜토리얼, 운영안, 대본, 평가결과를 영향 목록으로 묶는다. 과거 세션은 당시 규칙 버전으로 재생하고, 현재 적용성은 STALE로 표시할 수 있다. 기존 시나리오를 새 규칙에 자동 맞춤 수정하지 않고 diff·재검토를 요구한다.
## 08.4 부족한 자료의 처리
대외비 원본을 얻지 못하면 공개 정보로 구성한 부분과 실제 적용성이 미확인인 부분을 분리한다. 원본 제공 대신 비식별 조항·역할표·검수 회신·제한 열람 등 대체 증거를 받을 수 있다. ‘자료가 없으므로 어떤 값이든 사용’과 ‘회신 전 모든 개발 중단’ 모두 금지한다. 영향을 받는 교육 활성화·정량 예측·대본 승인 단계만 보류한다.
## 08.5 고객 검수 업무도 비용·증거로 기록
규칙 후보별 추출·원문 확인·적용 검토·합의·재작업 인시를 기록한다. 개발자가 대신 입력·검수한 비용을 사용시간 비교에서 제거하지 않는다. 문서 미취득·판본 불명·관할 충돌은 각각 다른 상태이며, 확인된 공학 불변식까지 함께 비활성화할 이유는 아니다. [REQ-078] [REQ-079] [REQ-080]
# 09. 랜덤 시나리오의 생성·범위·재현성
## 09.1 생성 입력
ScenarioSpec은 공간/기관/매뉴얼 버전, 훈련목표, 사건 계열, 가용자원, 외부 접근 모델, 인원 그룹, 정보 전달 조건, 모델 적용영역, 종료 조건을 갖는다. 분포와 상관관계는 근거가 있는 데이터 또는 표시된 설계 가정으로 등록한다. 기본 seed, 생성기 버전과 실제 추출값을 함께 저장한다.
## 09.2 조건부 생성 절차
선택 목표와 사용 가능한 모델을 확인한 뒤 사건 그래프를 구성한다. 공간·자원·시간·인과 관계 제약을 검사하고, 적합한 조합만 실행 후보로 제공한다. 동일 사건에서 서로 관련된 인원·시설 상태·도착 조건을 독립 난수로 무작정 생성하지 않는다. 실패한 생성 시도는 이유를 기록하고 제한된 횟수 후 조건 조정을 요구한다.
생성기가 항상 쉽게 성공하는 조건만 남겨 편향을 만들지 않도록 생성/거부 사유와 분포를 기록한다. 무리한 조합을 제거하는 것과 어려운 정당한 사례를 제거하는 것을 구분한다. 추가지원이 필요한 유형과 지원해도 모델상 판단할 수 없는 유형을 분리한다.
## 09.3 운영안과 외부 조건 분리
작성자가 조정하는 업무 배정·조건부 협조 규칙은 OperationalPlan이다. 외부 보고의 지연 법칙, 외부 인원 유입, 사용 가능한 기관 상태는 ScenarioSpec이다. 조치로 달라지는 혼잡·정보 생성·후속 도착을 고정 외생 이벤트로 오분류하지 않는다. A/B 비교에서는 동일한 외부 확률 혁신과 조건부 생성 규칙을 결속하되, 사용자 조치가 만든 내생 결과는 각 실행에서 재계산한다.
## 09.4 생성 결과 자격
FEASIBLE_WITHIN_MODEL, ESCALATION_REQUIRED, CONFLICTED_INPUT, UNSUPPORTED_DOMAIN을 구분한다. 공조 규칙 검사를 통과한 것이 현장 안전성을 입증하지는 않는다. 유효범위 밖 시나리오를 개발 실험으로 돌릴 수는 있어도 정상 검증 결과와 같은 표로 자동 순위화하지 않는다.
# 10. 시간 제어·스냅샷·분기·운영안 비교
## 10.1 시간 의미
wall clock, simulation time, observedAt, receivedAt, authoredAt을 구분한다. 일시정지는 분석용이며 결과의 시간통계를 왜곡하지 않게 별도 기록한다. 배속은 요청값과 실제 달성값을 표시한다. solver가 따라오지 못하면 과거장을 최신처럼 반복해 표시하지 않고 계산 대기 상태를 표시한다.
## 10.2 스냅샷 범위
스냅샷에는 공간·개체 상태, 기관별 정보, 업무망, 예약·회복/재보급, 전달 중 메시지, 난수 스트림, solver 내부 상태 또는 재시작 가능한 checkpoint, 버전·파일해시가 포함된다. rollback을 지원하지 않는 solver는 가장 가까운 적법 checkpoint부터 재계산한다. 정확 재개가 불가능하면 branch를 새 초기화 실행으로 분류한다.
원본 실행은 불변이다. 분기는 부모 session·sequence·snapshot hash를 참조한다. 동일 이벤트를 재전달해도 외부 효과는 한 번만 적용한다. 취소/실패/분기가 자원을 중복 생성하거나 해제하지 않아야 한다. 사후 작성 메모를 과거 이벤트의 원래 의도로 덮어쓰지 않는다.
## 10.3 비교 설계
한 쌍의 A/B는 같은 맵·규칙·모델·외생 조건 계약으로 시작한다. 그다음 세션·조건을 바꿔 반복 비교한다. 결과는 제약 위반과 다목적 성과를 나눠 제시한다. 허용되지 않는 역할 위반이나 필수 인계 누락을 빠른 종료시간으로 상쇄하지 않는다.
핵심 지표는 업무 누락, 권한 충돌, 자원 중복, 정보 대기, 경로·공간 점유 지연, 인계 완료, 가용자원 부담, 운영 복잡도, 검증된 경우에만 물리 출력이다. Pareto 비지배 대안을 표시하고 사용자 선택 이유를 남긴다. ‘보편 최적’ 대신 ‘시험한 조건과 모델 범위 내 비교’라는 표현을 사용한다.
통계 계획은 선택 전에 고정한다. 초기 30쌍은 계산예산 제안이며 최종 표본수는 변동·목표 정밀도와 사전 정한 종료 규칙으로 정한다. 30회 무사고가 안전성을 입증하지 않는다. 개발 중 좋아 보이는 실행만 골라 비교하지 않으며 선정용 조건과 최종 평가용 조건을 분리한다.
## 10.4 변경 영향과 안전한 부분 재실행
변경은 표시용, 계획/규칙, 공간/물성, 외생조건 변경으로 분류한다. 영향 그래프에서 변경된 입력과 파생결과를 연결하고 dirty 집합·재검토 이유를 보여준다. 그래프가 불완전하거나 물리 파급을 한정할 수 없으면 부분 재계산 대신 더 넓은 재계산으로 전환한다. 관계가 등록되지 않았다는 이유로 영향이 없다고 판정하지 않는다.
캐시는 input/version/config/hash가 같고 해당 출력의 유효성이 유지될 때만 재사용한다. 무효화는 원본 로그를 지우지 않고 현재 사용 자격을 STALE로 바꾼다. 빠른 재실행과 전체 재실행의 의미 상태·QoI가 사전 기준 내에서 일치해야 한다. 수행 불가 시 원인과 전체 재실행 선택을 제공한다. [REQ-084]
## 10.5 비교 가능한 실행과 비교 불가 결과
지원 모델·규칙·평가 수량이 다른 결과는 같은 순위표에 섞지 않는다. 일부 공조 지표만 공통이면 그 범위만 비교한다. 여러 시행의 분포, 조건별 순위 안정성, 제약 위반·실패·미완료를 함께 제공한다. 가정 변화로 순위가 뒤집히거나 차이가 불확도 이내이면 ‘우열 불명’으로 남긴다. 작성자가 운영안을 최종 선택하며 시스템은 보편적 최적·실제 피해 감소를 자동 주장하지 않는다.
# 11. 시뮬레이션 계산 모델과 SOTA 선정 기준
## 11.1 채택 원칙
최종 제품에는 규칙·공조, 사람 이동, 해당 시나리오의 화재/연기·교통/차량·자원 운영을 결합한다. 모든 재난을 하나의 엔진으로 계산하지 않는다. 최신 학습모델은 강한 후보이지만 검증된 기준 모델보다 정확도가 나쁘거나 상태 복원이 안 되면 채택하지 않는다. 단순 게임용 숫자와 VFX를 현실 계산의 대체로 쓰지 않는 것이 필수 요구다.
선정 과정은 현상·사용목적·필요 입력 정의 → 기준모델과 최신 후보 실행 → 독립 관측·기준 계산 비교 → 계산 비용·불확도·복구/분기 검사 → 적용영역 승인이다. 모델별 코드는 재현 가능한 commit, 가중치는 revision·해시, 입력과 전처리는 파일 해시로 잠근다.
## 11.2 기술 구성표

TAPAAL은 timed/colored/stochastic net과 시뮬레이션·검증 도구를 제공한다. FDS 공식 매뉴얼 페이지에는 6.11.1이 표시되며 저속 화재·열·연기를 대상으로 한다. JuPedSim v1.4.0 공개에는 V3와 WarpDriver가 포함된다. 위 구성은 이번 PRD에서 해당 기능 문서를 확인한 후보이며 설치·현장 실행 합격을 뜻하지 않는다. TECH-TAPAAL TECH-FDS TECH-FDS-SCOPE TECH-JPS14
## 11.3 업무·자원 계산
업무망 marking M은 각 팀·개인·장비·정보·권한 토큰의 상태다. 전이 u가 허용되면 M_next = M + C·u이며 시간 조건, 적용 rule guard, 기관 권한, 필요한 실제 토큰, 완료 증거를 함께 검사한다. 색상 토큰은 기관/자원 유형을 표현한다. 추상 net과 구현 런타임의 전이 의미를 동일 fixture로 대조한다. 상태공간 제한/timeout은 미검증이지 통과가 아니다. TECH-TAPAAL
자원 r의 점유 불변식은 Σ_j a[j,r]·x[j,t] ≤ C[r,t]다. 수량 제약과 함께 개인 ID·차량 승무원·장비 소유권의 중복을 검사한다. 예약은 모두 성공하거나 자신이 확보한 부분만 롤백한다. 가용량 변화·취소·지휘 인계·분기에서 보존되어야 한다.
업무 시작시각은 단순 FIFO가 아니라 start_j = max(요청도착, 선행완료, 정보확인, 자원가용, 공간도달, 적용승인)이라는 동기 조건의 결과다. 각 항목이 UNKNOWN이면 임의 0으로 채우지 않는다. 실제 소요시간은 작업유형·인력·장비·환경 조건에 대한 근거 있는 분포로 모델링한다. 데이터 없이 모두 지수분포·고정 30초로 가정하지 않는다. 임시 값은 개발 전용으로 구분하고 최종 보정자료와 교체한다.
## 11.4 화재·연기·열 계산

# 12. 다중 엔진 결합·시간·불확도 계약
## 12.1 하나의 물리량에는 하나의 소유자
OperationalKernel은 업무·권한·예약·메시지의 정본, PedestrianAdapter는 선택한 인물 이동의 정본, TrafficAdapter는 외부 차량 이동의 정본, HazardAdapter는 검증된 열·연기장의 정본이다. Unity는 입력과 표현을 담당한다. 결합 경계마다 위치·온도·유량·문 상태의 소유자를 명시한다. 같은 양을 두 엔진이 덮어쓰지 않는다.
## 12.2 이벤트와 연속 계산의 결합
명령은 durable event로 먼저 기록하고 사전조건 검사를 거쳐 승인된 상태 변화만 적용한다. 엔진별 dt는 현상·solver 안정성·수렴 조건에 따라 선택한다. 공통 교환 시점에는 같은 scenario time과 boundary revision을 사용한다. 보간이 필요한 경우 어떤 양을 어떻게 전달했고 보존량 오차가 얼마인지 기록한다. 모든 엔진을 무조건 60Hz로 돌리지 않는다.
문 개폐, 경로 상태 변화, 장비 작동 등 불연속 이벤트에서 경계를 재동기화한다. 비동기 결과에는 계산시각·유효시각·버전이 포함돼야 한다. 오래된 결과를 현재 필드로 덮지 않는다. 동작 지연이 커지면 가상 시간을 제어하거나 평가 자격을 보류하고, 렌더 프레임을 맞추려고 물리 dt를 조용히 키우지 않는다.
FMI는 선택적 교환 수단이다. 어댑터가 FMI나 상태 직렬화를 지원하는지 확인하기 전 이식성·rollback을 보장하지 않는다. 초기에는 명시적 protocol과 프로세스 경계를 사용할 수 있다. STD-FMI
## 12.3 불확도와 민감도
측정 불확도, 입력 가정, 수치 오차, 모델 편향, 학습 불확도를 구분한다. 공간·물성·반응시간 등의 불확도는 결과 QoI와 운영안 순위의 변동으로 전파해 비교한다. 결과 차이가 불확도와 비슷하면 ‘우열 불명’으로 표시한다.
정량 비교 예시는 e = |q_sim − q_obs|, 허용 판단은 사전 고정한 단위·절대/상대 허용오차·불확도 기준에 따른다. 0에 가까운 관측값의 상대오차 폭증을 피하도록 기준 scale과 절대오차를 함께 정의한다. 기준은 테스트 후 좋은 결과에 맞춰 완화하지 않는다.
## 12.4 현실 기준과 가상 분기의 분리
REALITY_BASELINE은 출처가 있는 실제 공간·시설·상태 관측으로 갱신한다. SCENARIO_BRANCH는 가상의 사건·운영안으로 변경된다. 게임에서 문을 열었다고 실제 문이 열렸다는 관측을 생성하지 않는다. 실제 대응물을 데이터로 연결하고 지정 빈도·충실도로 갱신한다는 디지털 트윈의 의미를 만족한 범위만 트윈 자격으로 표기한다. STD-DTC

## 13.5 실제 도입 환경과 비용 경계
현장 실증 전 설치 권한·운영체제·GPU/메모리·네트워크·보관·외부 전송 정책을 환경 계약으로 고정한다. 외부 LLM·원격 solver는 기본 자동 전송하지 않고 허용 정책에 따라 사용한다. 오프라인에서는 확보된 근거·저장·수동 편집과 로컬에서 지원하는 계산을 유지하며, 필요한 모델이 없으면 제한을 표시한다.
외부 서비스 장애·비용 상한 도달·과거 결과 재사용·출력 실패를 각각 기록한다. 데이터만 바꿔 새 현장을 추가하는 작업과 코어 코드를 새로 쓰는 작업을 구분해 고객별 맞춤 비용을 측정한다. 공개용 패키지에는 제한 원본·개인정보·계정키를 넣지 않는다. [REQ-087] [REQ-088]
# 14. 플레이 로그 기반 운영안·대본 자동화
## 14.1 자동화가 시작되는 곳
운영 실험 도중 작성자는 중요한 판단을 북마크하고 조건·이유를 적는다. 실행 뒤 AI는 로그의 사실과 병목을 설명하고, 작성자가 선택한 행동을 조건부 운영 규칙 후보로 정리한다. 과거 입력을 시간대로 복사하는 대신 역할·선행 조건·요청·인계·예외를 갖춘 재사용 가능한 운영안을 만든다.
처음부터 플레이가 없는 상황 템플릿을 생성할 수는 있지만 보조 기능이다. 핵심 성공은 작성자가 시뮬레이션을 통해 운영안을 선택·수정했으며 그 근거가 대본으로 이어지는 것이다. 자동 생성된 대본이 원인이고 플레이가 확인 절차인 제품으로 방향을 바꾸지 않는다.
## 14.2 기록·추론·권고의 분리
OBSERVED_IN_RUN, AUTHOR_ANNOTATION, HYPOTHESIS, MANUAL_SUPPORTED_PROPOSAL, REVIEWED_INSTRUCTION을 문장/단계 단위로 구분한다. 실제 수행 문장에는 event ID와 버전을, 사용자 이유에는 annotation 시각을, 권고에는 적용 가능한 source clause와 검수 결정을 연결한다. 로그에 없다는 사실을 미수행으로 단정하지 않는다. 기록 누락 구간은 불확실성으로 표시한다.
시간 차이·예약·경로 존재·상태 결과는 결정적 코드와 solver 기록으로 계산한다. LLM은 숫자를 재계산하거나 성공 상태를 꾸미지 않는다. 선후관계를 인과로 표현하려면 모델 내 반사실 비교 등의 추가 근거와 해당 범위 표기가 필요하다. ‘현실 인과가 입증됐다’는 표현은 별도 현장 증거 없이는 금지한다.
## 14.3 대본 출력

대본의 예정시간과 특정 실행에서 관측된 시간을 다른 필드로 둔다. 고정 시간과 사건 조건을 혼합할 수 있으며, 선행 완료가 필요한 부분을 임의 시각으로 강제하지 않는다. 문서와 실행 데이터는 같은 공통 모델에서 생성한다. 출력은 JSON과 읽기용 Markdown/DOCX를 기본으로 하고, PDF/HWPX 등 기관 양식은 제공 템플릿과 호환성 확인 후 지원한다. xAPI 등 교육 이력 교환은 선택적이며 원시 운영 로그를 대체하지 않는다. STD-XAPI REF-MSEL
## 14.4 리뷰·승인·재실행
초안 편집은 원시 로그를 수정하지 않는다. 승인에는 주체·역할·사유·버전·적용범위·근거·시각이 필요하다. 내용·맵·매뉴얼·모델의 의미 있는 변경은 관련 승인을 만료시키고 diff 검토를 요구한다. APPROVED_FOR_SIMULATION, REVIEWED_FOR_FIELD_EXERCISE, AUTHORIZED_FOR_NAMED_USE를 구분한다. 프로그램 UI에서 누른 승인이 법적·기관적 권한을 자동 부여하지 않는다.
새 실행은 새 session·독립 입력·새 결과를 만든다. 리플레이를 다시 틀거나 사용자 A의 클릭을 자동 반복하는 것을 다른 운영안의 재훈련으로 표시하지 않는다.
## 14.5 AI 평가·실패 처리
모델·prompt·retrieval index·규칙 bundle을 고정해 사실성, 근거 정확성, 미확인 처리, 역할/객체 존재성, 보안과 지연을 평가한다. 문맥은 source revision·기관·사건으로 좁혀 읽는다. 도구 출력·문서·사용자 메모의 지시문은 데이터일 뿐 시스템 권한이 아니다. 비용 상한·호출 timeout·개인정보 반출 정책을 적용한다. 실패 시 수동 작성과 검증된 타임라인은 계속 사용 가능해야 한다.
## 14.6 고객 양식과 수정·승인까지의 마지막 구간
TemplateProfile에 고객이 실제 제출하는 형식·판본·필수 열·역할별 서식·지원 가능한 출력기·검수자를 결속한다. 기본 JSON·Markdown·DOCX를 제공하되 HWPX/PDF 또는 다른 양식의 지원은 실제 템플릿을 열고 반환을 검증한 경우에만 표시한다. DOCX 생성 성공을 고객 HWPX 양식 지원으로 바꾸지 않는다.
작성자가 외부 편집기에서 수정한 내용은 운영안 의미 변경, 편집·서식 변경, 검토 메모로 나눈다. 의미 변화는 ScriptStepId와 diff를 이용해 운영안에 반영하고 재실행·재검토한다. 이력 손실 없이 재가져오기를 지원하지 못하는 형식은 수동 reconciliation과 소요시간을 표시한다. 자동 왕복 변환을 약속하지 않는다.
완료 시점은 파일 생성 시점이 아니라 사전 품질 기준을 충족한 검토 가능한 대본이 나온 시점이다. 기관 검수자의 의미 수정량과 출력 후 서식 수작업도 시간 지표에 포함한다. [REQ-086]
# 15. AI-native 데이터·온톨로지·추적성 계약
## 15.1 개념 계층

# 16. 성공 지표·사용자 연구·정량 정확도
## 16.1 핵심 성과와 네 가지 시간
주 성과는 품질 기준을 충족한 운영안·대본까지의 총인시와 중대한 공조 모순의 잔존이다. 대본 생성속도·플레이 시간·그래픽 품질만으로 효용을 승인하지 않는다. [REQ-069] [REQ-079] [REQ-080]

시간 관측 최소 필드는 caseId, participantCode, activityId, role, start, end, clockBasis, category, assistance, sourceType, completeness, artifactRef다. 자기보고·문서 복원·직접 관찰은 별도로 보고한다. 개발자의 대리 입력, 교육, 규칙·공간 준비, 기관 검수, 출력 재편집, 유지보수를 숨기지 않는다. DISC-05
## 16.2 최초 구축과 반복 사용의 비용
T_new(N) = T_initial + Σ(T_input + T_operate + T_attended_compute + T_review + T_export) + T_maintenance(N)
모든 T는 사람 작업량 단위다. T_initial에는 설치·교육·자료 정제·규칙 검수·현장 모델 준비를 포함한다. 무인 solver 비용·API비·저장·라이선스·지원은 별도 금액과 경과시간으로 기록한다. 일반 코어 R&D와 고객별 초기 설정은 구별해서 제시하되 고객별 대리 작업을 제거하지 않는다.
반복 유지보수를 포함한 건당 순절감 Δ가 양수일 때만 N_break_even = ceil(T_initial / Δ)를 추정한다. Δ≤0 또는 고객의 재사용 빈도가 미확인이라면 시간 절감·회수 가능성은 미입증이다. 역할별 단가 없이 인시를 임의 금액으로 바꾸지 않는다.
## 16.3 최근 업무 발견 조사
제안 표본은 최근 작성 경험자 6명, 기관 협조·검수자 3명, 자료·정보화 담당 1명이다. 모집·관찰은 미실행이며 겹치는 역할은 사람 수로 중복 세지 않는다. 최근 초안·최종본·수정 의견·검토 일정·양식을 함께 보며 변경 이유, 재작업량, 회신 지연, 데이터 제공 가능성, 승인·도입 경로를 확인한다. “쓰고 싶은가”라는 호감만으로 효용을 판정하지 않는다. [REQ-077] [REQ-078]
## 16.4 A/B/C 비교: 3D의 기여를 분리

B는 연구용 비교 조건이지 세 번째 사용자 모드나 제품의 새로운 기본 방향이 아니다. A에서 실제로 쓰는 AI를 일부러 금지해 이득을 부풀리지 않는다. B/C는 모델·정보·AI·도움·초기 준비 수준을 같게 잠근다. A와 B/C의 준비비 차이는 최초 비용으로 남긴다. [REQ-081]
8–12명은 형성적 표본 제안이다. 일반 모집단 효과·안전성을 입증할 검정력 근거는 아니다. 순서를 균형화하고 동등 난이도의 별도 과제를 쓴다. 같은 정답을 외워 개선되는 효과, 제작자 지원, 연습 횟수를 기록한다. 평가자는 가능한 한 도구 조건을 가린 산출물을 사전 rubric으로 검토한다.
평가 과제는 원본 열기 → 자원·보고 조건 변경 → 운영안 실행 → 문제 설명 → 수정 비교 → 실제 양식 출력이다. 심어놓은 알려진 오류 시험과 별도의 허용된 실제 보류 사례를 둘 다 쓴다. 개발한 사례에서의 회귀 통과를 독립 검증으로 바꾸지 않는다.
## 16.5 사전 목표와 실패 처리

20%는 종전 v10의 30% 가설을 대체하는 기획 기준이며 이미 개선됐다는 수치가 아니다. 첫 평가 전에 기준·품질 rubric·표본·종료 규칙을 고정한다. 실패 결과를 본 뒤 기준을 완화하지 않는다.
완료한 사람만 뽑아 빠른 도구라고 보고하지 않는다. 모든 시도의 완료율을 먼저 제시하고 완수 과제의 조건부 시간·제한시간 내 미완료·도움·탈락을 별도 보고한다. 표본과 사례 수가 부족하면 INCONCLUSIVE로 남긴다. 작은 표본에서 안전성·전국 평균을 일반화하지 않는다. [REQ-082]
## 16.6 정량 모델과 현실 정확도는 별도 시험
QoIContract는 목적·대상·조건영역·단위·관측·보정/검증 분할·오차 지표·허용오차·불확도·검수자·동결 시점·해시를 갖는다. 숫자가 없으면 성능 합격이 아니라 검증 계약 미완료다.

조작·운영·매뉴얼·기하/모델·재현/비교·대본·시스템·현장 활용을 각각 검사한다. 현재 문서에 ‘계획 AAA’ 점수를 재발급하지 않는다. 중요한 결함을 평균점수로 상쇄하거나 문서 검사 숫자를 실제 제품 품질로 사용하지 않는다.

고정 입력·버전 → 실패 재현 → 원인과 한정 수정 → 동일 시험 → 새로운 보류 사례 재검증의 순서다. 반복 예산은 작업마다 사전 설정한다. 같은 결함의 재발이나 필요한 입력의 부재가 지속되면 해당 단계만 설계·자료로 반환한다. 무제한 문서 루프·임계값 완화·로그 없는 PASS는 금지한다.

## 19.4 판정 규칙
PASS / FAIL / NOT_EVALUATED / INCONCLUSIVE / STALE / NOT_APPLICABLE을 구분한다. NOT_APPLICABLE에는 승인된 범위 제외 사유가 필요하다. 필수 입력·독립 자료가 없으면 합격이 아니라 NOT_EVALUATED다. 표본이 부족하거나 검수자 의견이 해결되지 않으면 INCONCLUSIVE다. 결과와 연결된 입력·판본이 바뀌면 영향받는 자격은 STALE이다.

# 부록 A. 문서와 원문 탐색
REQUIREMENTS.md는 전체 원자 요구와 시험의 요약, TRACEABILITY.md는 UR→REQ→EP→AT, CRITIQUE_TO_REQUIREMENTS.md는 C→REQ→AT를 제공한다. VALIDATION_PROTOCOL.md는 사용자·시간·물리·사업 평가를 구별한다. SOURCES.md는 기존 외부 원문 링크와 이번 개정의 재검증 한계를 제공한다.
문서의 [MAN-…], [TECH-…], [STD-…], [DISC-…], [FREE-…]는 출처 ID, [REQ-…]는 요구 ID다. 특정 출처를 다시 읽었다고 제품 검증이 되는 것은 아니다. 무료 에셋은 FREE_ASSET_CATALOG.md와 contracts/free-assets.json에서 필요한 ID만 선택한다. 오래된 PRD와 조사자료는 history/에 있고 현재 실행 지시가 아니다.
