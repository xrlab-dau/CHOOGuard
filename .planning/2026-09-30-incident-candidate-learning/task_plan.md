# 비상상황 후보 생성을 맵에서 학습한다 (방향 B)

`develop d7773cdc` 기준. 사용자 요구: **부산역 맵을 바탕으로 비상상황을 만드는 머신러닝.**
세 갈래(A 로컬 증류 · B 후보 생성 학습 · C 시나리오 사전 생성) 중 **B** 를 택했다.

## 무엇을 바꾸려는 것인가

지금 후보는 **사람이 쓴 여섯 종**이다(`IncidentDirector.Origins()`, L388).

    보조배터리 과열 · 쓰러짐 · 가방 방치 · 에스컬레이터 넘어짐 · 문 끼임 · 지진

PR #259 가 이를 28종으로 늘리지만 **여전히 사람이 쓴 목록**이다. B 는 그 목록을 맵에서
끌어내는 것이다 — 역 안에 무엇이 있고 그것들이 어떤 상태가 될 수 있는지에서.

## 절대 깨면 안 되는 것

`.agents/rules/jev-emergency-composition.md` 가 상시 하드룰이다. 그중 이 작업에 직결되는 것:

- **후보는 물리적으로 가능해야 한다.** 지금은 코드가 실제 오브젝트를 집어서 만들기 때문에
  불가능한 후보가 나올 수 없다. 모델이 후보를 제안하면 **이 보증이 깨진다.**
- **JEV 는 코드가 만든 후보만 고른다**(`JevClient.Parse()` 가 후보 밖의 답을 버린다).
  모델이 후보를 만들더라도 이 경계는 그대로 둔다.
- **목록·시나리오 ID 테이블 금지.** 학습 결과를 '사건 목록'으로 굳히면 규칙 위반이다.

그래서 이 설계의 중심은 **유효성 관문**이다.

    모델이 제안  →  코드가 살아 있는 오브젝트로 해석  →  전제 조건 검사  →  통과한 것만 JEV 로

해석되지 않거나 전제가 불충족이면 **버린다.** 모델이 무엇을 상상하든 월드에 없는 일은 일어나지 않는다.

## 단계

### A. 맵이 무엇을 줄 수 있는지 센다 — 바꾸지 않는다
역 안의 **어포던스**를 전수 조사한다. 사람이 쓴 여섯 종이 아니라, 실제로 존재하는 것들.

- `station-points.json` — zone 10개, 지점 1,137개(`Exit·Counter·Shop·Wait·Office·Seat·Chair·Toilet·PlatformWait·Meet`)
- 설비 — 에스컬레이터, 엘리베이터, 개집표기, 역사 출입문, 소방 설비, AED
  (`.planning/2026-09-28-world-interaction/research.md` 에 조사돼 있다)
- 열차 — KTX-산천 10량, 문·좌석·통로, 운행 주기
- 승객 속성 — `Activity` 11종, `Elderly`, `Luggage`, `CarriesPowerBank`, `TrainSeat`
- 씬 실물 — 매장·카페·화장실(1·2·3층), 매달린 구조물, 승강장 가장자리

판정: **지금 후보가 쓰는 것이 어포던스 전체의 몇 %인가.** 이 수치가 B 의 값을 정한다.
20% 미만이면 학습 이전에 규칙만 넓혀도 효과가 크다는 뜻이고, 80% 이상이면 B 의 값이 적다.

### B. 학습 데이터가 실제로 쌓이는지 확인한다
`JevClient.Log()` 가 요청마다 `state`·`questions`·`answers` 를 JSONL 로 남긴다
(`EmergencySession.cs:136`). `ShiftLog.Compositions` 는 `t·kind·key·magnitude·by·detail`.

키가 방금 유효해졌으므로(`GET /v1/models` → 200) **실제 근무를 몇 번 돌려 로그를 받는다.**
한 근무에서 몇 건이 쌓이는지, 입력 토큰이 얼마인지 잰다. 비용이 여기서 정해진다.

판정: 한 근무당 유효 표본이 30건 미만이면 학습 데이터로 모으는 비용이 크다. 그때는
A 단계 결과만으로 규칙을 넓히는 쪽이 낫다.

### C. 제안기를 만든다 — 학습은 마지막이다
순서를 뒤집지 않는다. 먼저 **규칙 기반 어포던스 제안기**를 만들어 후보 수가 실제로 늘어나는지
본다. 그것이 되고 나서야 학습이 무엇을 더 하는지 물을 수 있다.

1. 어포던스 → 전이 후보로 푸는 코드. 오브젝트 하나당 가능한 상태 변화를 열거한다.
2. 유효성 관문. 살아 있는 오브젝트 참조 + 전제 조건.
3. 기존 여섯 종을 이 틀로 다시 표현해 **동작이 같은지** 확인한다(회귀).
4. 그 다음에 학습 — JEV 로그로 "어떤 후보가 골라지는가"의 사전분포를 학습해 제안 순위를 매긴다.

### D. 검증
- 후보가 늘어도 **불가능한 후보가 0건**인지. 유효성 관문이 핵심이므로 이것이 실패하면 전부 무효다.
- 종류·장소가 실제로 다양해졌는지. 근무를 여러 번 돌려 `kind`·`Where` 분포를 센다.
- 기존 시험이 깨지지 않는지. 규칙 6: 특정 사건을 기대값으로 두지 말고 불변조건을 검사한다.

## 하지 않을 것

- **시나리오를 미리 생성해 저장하는 것.** 규칙 금지 조항이다.
- **JEV 를 후보 생성에 쓰는 것.** JEV 는 고르고 점수를 매기는 역할이고, 그 경계가 코드로 강제돼 있다.
- **PR #259 와 겹치는 작업.** 그쪽이 원인을 28종으로 늘리는 중이다. 머지 전에 같은 곳을 건드리면 충돌한다.

## 멈출 조건

- A 에서 지금 후보가 어포던스의 대부분을 이미 덮고 있으면 → B 의 값이 없다. 보고하고 멈춘다.
- B 에서 근무당 표본이 너무 적으면 → 학습을 뒤로 미루고 규칙 확장만 제안한다.
- C-3 회귀에서 기존 여섯 종의 동작이 달라지면 → 되돌리고 원인을 찾을 때까지 진행하지 않는다.
- 어느 단계든 유효성 관문이 불가능한 후보를 통과시키면 → 즉시 멈춘다.

## PM 확인이 필요한 지점

A·B 단계는 읽기·측정뿐이라 지금 해도 되지만, **C 착수 전에 #259 상태를 확인**한다.
