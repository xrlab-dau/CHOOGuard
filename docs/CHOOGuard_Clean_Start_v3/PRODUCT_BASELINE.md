# CHOOGuard — 새 구축 제품 기준

문서 기준일: 2026-09-19. 제품 요구를 유지하되 구현은 빈 저장소·새 Unity 프로젝트를 전제로 한다. 기존 코드·에픽·작업 명세·공간 식별자·테스트 성공 이력은 시작 조건이 아니다. 이 문서는 해당 분야의 과거 실행 지시보다 우선한다.

## 1. 누구의 어떤 문제를 해결하는가
주 사용자는 같은 철도 현장이나 재사용 가능한 현장 묶음에서 다기관 비상대응 종합훈련을 반복 기획하는 시나리오 작성 담당자다. 목표는 단순 문장 자동 생성이 아니라 업무·역할·자원·정보·공간·시간 제약 아래 운영안을 실행하고 충돌·누락·대기를 확인해 더 정합한 운영안과 대본을 만드는 것이다.

제품은 Unity native PC다. RTS형 조작으로 팀·차량·업무를 선택하지만 반사신경 게임은 아니다. 전체 분석을 보는 작성자와, 자신에게 전달된 정보만 갖는 시뮬레이션 속 기관은 별개다.

## 2. 핵심 여정
현장 묶음 열기 → 상황 설정 → A안 운영 → 막힌 이유·근거 확인 → A를 보존하고 B로 분기 → 같은 외생조건/변형 조건 비교 → 작성자 선택 → 대본·근거 검토 → 실행형 데이터와 문서 출력 → 새 운영 실험.

필수 성공은 두 기관·소수 팀의 한 업무에서 요청·예약·이동/준비·수행·보고/인계가 실제로 이어지고, A의 문제를 B로 고쳐 차이를 설명·대본화하는 것이다. 맵이나 문서만 만들고 성공으로 처리하지 않는다.

## 3. 정확히 두 모드
`TUTORIAL`: 실제 훈련/검토된 매뉴얼을 바탕으로 안내·힌트 축소·복기를 제공한다. 공개 사례 재구성과 정확한 실제훈련 재현을 구별한다. 독립적인 업무 순서에는 여러 유효 대안을 허용한다.

`RANDOM_OPERATIONS_LAB`: 기관·공간·자원·인과·모델 범위가 맞는 조건부 사건을 만든다. 추가지원 필요와 미지원 계산을 구별한다. 정지·분기·분석·기관별 정보·solver 프로파일은 공통 도구이며 추가 제품모드가 아니다.

두 모드는 동일 운영·물리 코어를 쓴다. 힌트로 이동속도·장비·권한·물리결과를 바꾸지 않는다.

## 4. Unity 화면·입력
uGUI(Canvas) + TextMeshPro + 새 Input System을 기본 설계로 한다. WorldCamera가 실제 3D 현장을 직접 렌더링하고 그 위에 HUD, 접이식 조직 목록, 업무 inspector, command dock, 미니맵, 사건 타임라인을 둔다. 비교·대본은 같은 게임의 native overlay다.

입력 소유권: modal → text/IME → HUD → world selection/command → camera. pointer-down의 소유자는 up/cancel까지 유지한다. 버튼 클릭이 뒤의 팀 선택으로 새지 않으며 Space·Enter·Esc는 한글 입력 중 게임 명령이 되지 않는다. 목록·키보드 경로로도 핵심 작업을 수행한다.

## 5. 새로운 공간 기준
첫 현장은 외부 도착 경계–현장 업무 공간–맞이방–승강장–선택 객실이다. 부산역을 실제 참조 후보로 유지하되 자료에서 확인한 범위와 합성·추정 범위를 표시한다. 새 RegionId·EntityId·FrameId를 발급하고 특정 과거 구역 수나 ID 목록을 요구하지 않는다. 확장은 실제 공간 구성과 제품 필요성으로 결정한다.

동일 대상의 visual/collision-navigation/physical/semantic 표현을 분리하고 같은 ID·단위·버전을 공유한다. 기존 파일이 사라졌어도 두 공간+문 fixture를 새로 만들어 개발할 수 있다. 합성 fixture 성공을 실측 정확도의 증거로 쓰지는 않는다.

## 6. 운영 코어
한 run의 상태는 단일 writer가 결정한다. 명령 요청·접수·완료를 분리하고 권한·자원·정보·공간 조건을 재검사한다. 업무생명주기와 권한/정보/자원/이동/안전/근거 원인은 독립 축이다. 한 이유만 보여주지 않는다.

지원 요청은 타기관 직접 명령과 다르다. 팀 분리·승무원 변경·회복·재보급·수용/인계는 자원과 역할 상태를 바꾼다. 물리적 불가능은 강제하지만 매뉴얼 재량을 무조건 금지로 바꾸지 않는다.

## 7. 기록·비교
명령 수락 전 이벤트·receipt·예약·outbox를 원자 저장한다. 같은 요청의 재전달은 효과를 중복 적용하지 않는다. 기록은 변경하지 않고 새 revision/branch를 만든다.

정확 분기는 업무·예약·대기열·전달중 메시지·기관 지식·난수·worker 내부 상태 또는 검증된 재계산 경로가 있을 때만 허용한다. 외생 혁신은 A/B에 맞추고 사용자의 선택이 만든 내생 결과는 각 실행에서 계산한다. 불확도 안의 차이·실패·미완료·비교불가를 숨기지 않는다.

## 8. 물리 정확도
기술 후보는 사용사례별로 선택한다. 운영 모델은 이산사건과 자원 제약, 보행은 JuPedSim 등 비교 후보, 교통은 SUMO 등 현지 보정 후보, 화재·열·연기는 FDS 기준 계산, 가속은 검증된 ROM/PhysicsNeMo 후보를 사용한다. 이 이름은 설치·현장검증 완료를 뜻하지 않는다. 원문은 reference/sources.json에 연결한다.

각 수량은 한 모듈만 갱신한다. 시간·좌표·단위·경계 revision을 맞추며 실제 모델의 복원 능력을 확인한다. FDS를 기본적으로 배치 기준 계산으로 취급하고 임의 실시간 rollback을 가정하지 않는다. 느리면 계산대기/검증된 대안/평가보류를 표시하며 dt를 몰래 키우지 않는다.

독립 관측·수치수렴·QoI 오차·불확도·모델 유효범위·현실 갱신을 필요한 주장별로 검증한다. 실제 대응 최적성이나 피해 감소를 미검증 모델로 보장하지 않는다. 학부 프로젝트라는 이유로 최종 정확도 기준을 지우지 않는다.

## 9. 매뉴얼·AI·대본
RuleBundle은 원문/판본/기관/사건/예외/검수와 연결한다. AI는 규칙 후보·설명·수정안·대본 초안만 제공한다. 물리값·권한·완료·승인을 직접 수정할 권한이 없다. 외부 텍스트의 지시문은 자료일 뿐 실행 권한이 아니다.

실제 실행 사실·작성자 사후 설명·가설·근거 있는 제안·검수된 지시는 분리한다. 선택한 운영안에서 ScriptIR를 만들고 종합전개표·기관역할/협조·보고/안내·진행자 대본·평가·실행데이터를 같은 의미로 출력한다. 기관 양식은 실제 template 검증 뒤 지원하고 외부 편집의 수동 조정 비용도 기록한다.

## 10. 자료·에셋
무료 에셋 우선은 구매비 정책이지 제작·검수·계산 비용 0원 정책이 아니다. 기존 조사 링크는 검색 후보로 유지하되 현재 원본 취득·Unity 입고·실측 수용을 상속하지 않는다. 실행파일/DLL/코드가 포함된 archive는 별도 격리한다. 가공·배포·민감자료의 허용 범위를 기록한다.

## 11. 사용자 가치와 도입 검증
실제 작성자 최근 대본·수정·양식·투입시간을 조사한다. 기존 방식 A, 같은 코어의 표/타임라인 B, RTS C를 연구 조건으로 비교한다. B는 추가 제품모드가 아니다. 총인시·중대오류·완료율·검수수정·두 번째 자립사용을 확인한다. 20% 절감은 사전 협의할 탐색목표이며 성과가 아니다.

초기 입력·교육·개발자 도움·유인 계산대기·출력수정·유지보수를 포함한다. 미완료를 제외해 성과를 꾸미지 않는다. 사용자 조사·물리 검증·기관 수용·구매 판단은 별도 경로다.

## 12. 제외와 변경 경계
웹 UI/WebView, VR/HMD/XR 요구, 별도 FPS, 자유 건설·수익경영, 공격 최적화, 실설비 제어를 추가하지 않는다. 런타임 라이브러리가 모듈을 포함한다는 이유로 제품기능을 추가하지 않는다.

이 문서 작성은 원격 저장소 초기화·삭제·이슈 생성·assignee 변경·구현 착수가 아니다. 새 명세의 모든 제품시험 상태는 NOT_RUN이다. 외부자료와 과거 보고는 근거 후보이며 새 실행의 PASS가 아니다.
