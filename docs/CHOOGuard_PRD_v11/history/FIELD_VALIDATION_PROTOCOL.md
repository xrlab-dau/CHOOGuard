# 사용자·시간·제품 가치 검증 프로토콜

**상태: NOT_RUN.** 인터뷰나 사용자 실험을 이미 했다는 기록이 아니다. 안전성·현장 대응 효과를 검증하는 실제 재난 실험도 아니다.

## 1. 최근 업무를 기반으로 발견하기

제안 모집: 최근 합동훈련 대본 작성 경험이 있는 담당자 6명(가급적 3개 작성 조직), 기관별 협조·검수자 3명, 자료·정보화 담당자 1명. 겹치는 역할은 표기하고 독립 표본으로 중복 집계하지 않는다. 역할·업무 경험을 기준으로 모집하며 임의의 나이·게임 경험으로 배제하지 않는다.

사전 협조자료는 허용된 범위의 최초·최종 대본, 수정 의견·변경 이력, 자료 요청·협의 일정, 적용 매뉴얼 판본, 가용자원·공간 정보, 실제 제출 양식이다. 개인·보안정보는 비식별화하고 녹음·보관·외부 LLM 전송은 별도 동의·허용 범위에 따른다.

핵심 질문은 “사용하겠습니까?”가 아니라 다음과 같은 실제 과거 업무 질문이다.

1. 마지막으로 완성한 훈련 대본은 언제 어떤 계기로 시작했고 본인이 맡은 결과물은 무엇인가?
2. 실제 최초·최종 버전의 차이는 무엇이며, 가장 많은 재작업을 만든 변경은 무엇인가?
3. 직접 일한 시간, 여러 사람이 참여한 회의, 단순 회신 대기 시간을 구분할 수 있는가?
4. 어떤 공조·자원·공간 문제가 문서 검토 또는 예행연습에서 발견됐는가? 근거를 볼 수 있는가?
5. 해당 문제를 기존 도구·회의·전문가로 해결했을 때 효과와 부담은 무엇이었는가?
6. 실제 매뉴얼의 예외·재량·관할 문제는 누가 판단했고 어떻게 기록했는가?
7. 마지막 결과물의 제출 양식과 최종 승인자는 누구인가? 다시 편집해야 하는 부분은 무엇인가?
8. 실제 도입 때 자료·설치·모델 업데이트·유지보수를 책임질 수 있는 사람과 예산 단위는 무엇인가?
9. 다음 작성 건에서 허용된 사례와 검수 시간을 제공할 수 있는가? 이것은 계약 확약과는 구분한다.

사용자 발언은 기억 기반/문서 확인/관찰로 분류한다. 연구자가 대필한 추정 시간을 실측값으로 바꾸지 않는다. 해당 고객의 현재 도구가 문서·스프레드시트라는 가정도 직접 확인한다.

## 2. 시간관측

관측 단위는 `caseId × participantId × activityId`다. 시작·종료, 역할, 실제 활동, 동시 작업, 도움, 자료 준비 여부, 실패·재시도·검토 결과를 기록한다.

활동 구분: 자료 확보/규칙 검토/현장 모델 준비/교육/조건 입력/운영안 편집/실행 관찰/무인 계산/검토/회의/출력 수정/외부 회신 대기/유지보수.

같은 사람의 중첩 시간은 한 번만 계산한다. 회의 시간은 참여자별 실제 투입으로 합산한다. 무인 계산과 외부 대기는 캘린더 지연에 포함하되 사람 작업량에 중복 더하지 않는다. 별도 참가자 도움과 개발자의 대리 입력도 기록한다.

품질 기준을 못 맞춘 미완성 작업을 ‘짧게 끝났다’로 평가하지 않는다. 중단·시간제한 도달을 별도 결과로 남긴다. 기억으로 복원한 작업시간은 관찰시간과 섞지 않는다.

## 3. A/B/C 형성적 비교

A = 고객이 실제 사용하는 기존 도구·과정.  
B = 동일 데이터·AI·규칙·계산 코어 + 표/타임라인 UI(3D 제외).  
C = 동일 코어 + CHOOGuard RTS·공간 조작.

B는 실제 제품의 새 사용자 모드가 아닌 연구용 비교 조건이다. 기본 제품은 튜토리얼/일반 모드 둘을 유지한다.

8~12명은 제안한 형성적 표본이며, 타겟 인구 전체의 효과 또는 실제 재난 결과를 추론하는 검정력 근거는 없다. 가능한 참가자 경험을 기록하고 조건 순서 균형화·난이도 매칭·연습 효과 분리를 한다. 각 조건에서 사용할 사례는 동일 답안을 외우지 않도록 별도이되 요구 역할·공조 수·자료 복잡도를 맞춘다.

필수 비교 과업: 대표 원본을 열기 → 한 자원·보고 조건 변경 → 운영안 실행·검토 → 문제 설명 → 수정안 비교 → 지정 양식 초안 출력. 평가자는 도구 조건을 가린 결과물을 사전 rubric으로 검토한다. 검토자 의견 불일치를 보존하고 합의 과정을 기록한다.

설계 중 함께 만든 사례와 테스트용 사례를 나눈다. 의도적으로 넣은 알려진 공조 결함으로 탐지율을 시험하되, 이것만으로 실제 결함 발견 능력이 입증됐다고 하지 않는다. 별도의 허용된 실제 미공개 사례를 이용한다.

## 4. 지표와 판정

주 지표는 품질 기준을 충족한 결과까지의 총인시와 중대한 결함 잔존이다. 보조 지표는 최초 유효 비교시간, 오경보, 근거 추적, 검수 수정량, 주관적 부담, 도움 요청, 두 번째 자립 사용이다.

제안 사전 목표: A 대비 중앙값 총인시 20% 이상 감소 + 사전 합의한 품질 저하 없음. C의 B 대비 공간 관련 오류 탐지·이해 이득과 총노력의 유지를 확인한다. 온보딩 30분·첫 유용한 비교 15분은 별도 탐색 목표이며 실제 분포를 함께 보고한다. 숫자는 고객과 사전 합의 후 고정하고 결과를 보고 바꾸지 않는다.

정확도는 분야별로 독립 평가한다. 권한·출처·완료 기록의 고정된 중요 시험세트에서 오류 0건을 요구할 수 있지만, 그 결과를 현실의 모든 사건에서 0오류라고 일반화하지 않는다. 생산성 결과와 실제 대응 성능은 분리한다.

## 5. 중단·수정 규칙

- 실제 대표 입력과 검수자 확보가 안 되면 대상 현장 정량 승인과 대규모 맞춤 모델링을 보류한다.
- 운영 실험은 가치가 있지만 3D로 작업량이 늘면 카메라·마이크로 조작·반복 플레이 부담을 줄이고 재평가한다.
- 구조화 도구만으로 동등한 품질·속도가 나오면 3D의 추가 범위를 재검토한다. 미리 숨기지 않는다.
- 모델이 검증 영역 밖이면 결과를 미검증으로 표시한다. 사용자가 흥미로워했다는 이유로 정밀 수용하지 않는다.
- 표본이 작거나 탈락이 많으면 결론 불충분으로 남기고 좋았던 사용자만 선별해 보고하지 않는다.
- 같은 데이터에서 수정을 반복해 통과한 결과는 개발 검증이다. 별도 새로운 사례에서 다시 시험한다.

## 6. 현실 전이와 사업성

정밀 적용은 현상별 독립 보정·검증 → 결합 검사 → 허용된 도상·시범훈련 → 기관의 해당 용도 검토 순으로 진행한다. 실제 위험을 일으키거나 운영설비를 직접 제어하지 않는다. 구매 의향 인터뷰, 파일럿 참여, 비용 승인, 계약 체결은 별도 단계로 기록한다.

실행 기록에는 `studyVersion, participantCode, taskCaseVersion, condition, order, dataReadiness, rawTimeLog, artifactHashes, reviewerBlindStatus, metrics, exclusions, failures, decision, limits`를 포함한다. 개인정보와 제한 자료는 공개 연구 패키지에 넣지 않는다.
