# CHOOGuard 제품 요구사항 정의서
## 현실 기반 철도 비상대응 운영 시뮬레이터

**문서 ID:** PRD-CHOOGUARD-OPS-010  
**버전:** 10.0.0 · **기준일:** 2026-09-18  
**문서 상태:** 사용자 요구 통합 설계안 / 개발·기관 수용 전  
**최종사용자:** 유관기관 비상대응 종합훈련 시나리오 작성 담당자  
**제품 플랫폼:** Unity 기반 PC 애플리케이션  
**기획 우선순위:** #222 연계 P0-0 / 신규 통합 목표 착수 1순위  
**정본:** 이 PRD와 연결된 요구사항·인수시험·데이터 계약. Word 문서는 동일 내용의 읽기용 배포본이다.

> 운영 시뮬레이션이 본체다. 시나리오 작성 담당자는 기관·팀·차량·업무를 RTS처럼 선택하고, 매뉴얼·공간·정보·자원·물리 제약 안에서 운영안을 시험한다. 같은 상황의 대안을 분기·비교해 선택한 운영안을 종합훈련 시나리오와 대본으로 전환한다.

‘SOTA’는 최신 이름의 최대 사용이 아니라, 2026-09-18에 확인한 연구·표준·공식 도구를 후보로 삼고 대상 철도 사용사례에서 정확성·비용·재현성·적용범위를 비교하는 기술 선정 원칙이다. 이 문서는 특정 모델이 세계 최고이거나 실제 제품이 AAA에 도달했다고 선언하지 않는다. 요구사항은 앞으로 충족해야 하는 계약이며 현재 실행 증거가 아니다.

## 00. 문서 사용법과 의사결정 상태

### 00.1 읽기 순서

제품·PM 담당자는 §01–05 → §16–20을 읽는다. Unity·운영 엔진 담당자는 §04–13 → 담당 요구사항을 읽는다. 규칙·AI 담당자는 §07–08, §14–15를 읽는다. 자산 담당자는 §06, §17과 자료 등록부를 읽는다. 검수자는 §16, §19와 `contracts/acceptance-tests.json`을 읽는다.

개발 LLM은 `START_HERE.md` → 현재 EP 작업의 `agent-packets/EPxx.json` → 해당 요구사항 ID → 필요한 원문만 읽는다. 관련성이 있다는 이유로 모든 매뉴얼과 옛 이슈를 입력하지 않는다. 요약으로 누락된 입력·권한·검증 조건을 임의 보충하지 않는다.

### 00.2 상태를 섞지 않는다

| 구분 | 현재 의미 |
|---|---|
| 사용자 요구 | 대화에서 명확하게 제시한 제품 방향. §02에서 추적한다. |
| 설계 결정 | 본 PRD가 채택한 구현·UX 방향. 사용자 최종 승인 대상이다. |
| 공개자료 사실 | 출처에서 확인한 기능·훈련 사실. 실제 현장 적용성은 별도다. |
| 제안 목표값 | 아래 성능·사용성 숫자. 측정 결과나 법정 기준이 아니다. |
| 미확인 입력 | 원문 개정판, 실제 편성·물성·현장 측정 등. 책임·소비 단계와 연결한다. |
| 제품 증거 | 구현 후 나온 원시 결과·재현 기록·검수 결정. 현재 NOT_RUN 또는 NOT_EVALUATED다. |

이 문서 작성으로 GitHub #222, 다른 이슈, 보호 브랜치, 기존 구현·배정은 변경되지 않는다. 현재 #222 v9를 조회했으며, 시나리오 작성자의 다기관 운영 실험과 최신 물리 정확도 요구를 반영한 본 PRD로 전환하려면 별도 이슈·work-order 마이그레이션이 필요하다. 과거 내부 ‘계획 AAA’와 테스트 횟수는 제품 품질 증거로 상속하지 않는다. [REPO-222]

## 01. 제품 비전과 해결할 문제

### 01.1 클라이언트 요구의 원문과 해석

**사용자가 전달한 클라이언트 요구:**

> 유관기관 비상대응 종합훈련 시나리오(대본)을 자동으로 작성하는 시스템을 구축할 경우, 다양한 유형의 비상상황을 사전에 구조화된 형태로 시뮬레이션할 수 있는 기반이 마련될 것으로 판단됨. 이를 통해 재난, 사고 유형별 대응 절차를 반복적으로 점검, 보완할 수 있으며, 기관 간 공조 체계와 역할 분담을 사전 검증하는 데에도 활용도가 높을 것으로 기대됨. 특히, 훈련 기획 시 시나리오 작성에 소요되는 시간과 인력을 절감함과 동시에, 보다 다변화, 고도화된 상황 설정이 가능해져 실효성 있는 비상대응 역량 강화에 기여할 수 있을 것으로 보임.

원문은 종합훈련 기획·공조 검토·대본 자동화를 요구한다. 최신 사용자 결정은 이를 **작성자가 직접 운영 시뮬레이션을 수행하는 경험**으로 구현하는 것이다. ‘대본을 먼저 자동 생성한 뒤 확인만 하는 프로그램’이나 ‘훈련생의 정답률을 평가하는 게임’으로 핵심을 바꾸지 않는다.

### 01.2 제품의 가치 가설

문서만으로 기관별 업무 순서·자원 점유·정보 전달·공간 접근의 충돌을 발견하기 어렵다는 문제를, 실행 가능한 운영안과 비교 가능한 결과로 해결한다. 이 어려움과 절감 효과는 현재 제품 가설이며 실제 작성 담당자 평가에서 확인한다. 성공은 생성 문장 수가 아니라 **검토 가능한 운영안을 만들 때까지의 총시간, 발견·수정한 결함, 근거 추적성과 재실행 가능성**으로 측정한다.

### 01.3 한 문장 제품 정의

**실제 철도 공간·기관별 매뉴얼·검증된 운영 및 물리 모델을 결합해 작성 담당자가 비상대응 운영안을 게임처럼 시험·비교·개선하고, 선택한 운영안을 근거가 연결된 종합훈련 시나리오·대본으로 출력하는 PC 운영 실험 도구.**

### 01.4 제품이 아닌 것

자유 건설·수익 경영 게임, 대테러 전투 게임, 물리 VFX 재생기, LLM 자유서술로 결과를 결정하는 시뮬레이터, 실제 설비 원격제어 도구, 기관의 안전 인증이나 임상 판단을 대신하는 시스템은 아니다. 공격 방법·무기 제작·취약점 악용 최적화는 제외한다. 사건은 대응 운영을 시험하기 위한 검토된 배경 조건으로 다룬다.

## 03. 사용자·권한·제품 범위

### 03.1 사용자와 시뮬레이션 속 기관은 다르다

| 사용자 역할 | 목적 | 허용 기능 |
|---|---|---|
| 운영안 작성자 / 주 사용자 | 상황을 시험하고 기관 공조 운영안을 개선 | 맵·자원·업무 선택, 일시정지, 분기, 비교, 대본 초안 |
| 매뉴얼 검수자 | 기관별 규칙의 개정판·적용성·예외 확인 | 규칙 후보 검토, 적용범위 승인·반려 |
| 모델 검수자 | 기하·물리·행동모델의 적용영역과 오차 확인 | 비교 실험, 자격 판정, 모델 버전 승인 |
| 교육 사용자 | 튜토리얼로 구조와 판단을 학습 | 안내된 실행, 힌트 감소, 복기 |
| 훈련 책임자 / 승인자 | 대본의 훈련 적용 가능 여부 판단 | 검토 의견, 지정 용도 승인, 버전 확정 |

같은 사람이 여러 역할을 맡을 수 있으나 제출·검수·승인 기록은 구분한다. 독립 검수가 필요한 gate는 작성자 자신의 확인만으로 통과시키지 않는다. 제품 내 작성자 권한은 **가상 세계를 설계하는 권한**이며 모든 기관에 실제 명령권을 갖는다는 뜻이 아니다.

### 03.2 시뮬레이션 속 조직

기관 → 조직단위 → 팀 → 개별 인력 → 차량·장비의 관계를 갖는다. 철도 운영·관제·기술복구, 소방·구조, 구급·의료, 경찰, 철도특별사법경찰, 지자체·시설지원이 초기 기능군이다. 군·전문기관은 적용 훈련에 실제 포함될 때 활성화한다. 기능군은 UX 분류이지 법적 조직도가 아니다. 코레일 공개 체계는 현장·관제·복구와 유관기관 협조를 구분한다. [MAN-KORAIL]

소속기관 내부 명령과 외부기관 지원 요청을 다른 메시지·권한으로 처리한다. 소방 SOP의 지휘권 규정을 근거로 경찰·철도·의료의 모든 권한을 하나의 게임 사령관 아래 합치지 않는다.

### 03.3 초기·최종 범위

초기 공간은 외부 도착 경계·현장 외부 업무 공간·맞이방·승강장·선택 객실을 잇는 하나의 연속 구간이다. 최종 확장 기준은 기존 13개 root RegionId를 보존하는 철도·광장·지하환승 공간이다. 알려진 합성 포털·임시 치수는 실물 정답으로 고정하지 않는다. 외부 기관의 건물 전체를 만들지 않고 지도 밖 자원 노드와 실제·가정 접근시간 모델로 연결한다.

첫 기술 검증은 두 기관·소수 팀으로 한다. 통합 제품의 초기 부하 가설은 6개 기능군, 선택 팀 16개, 대응 인력 64명, 일반인 120명, 도로차량 10대, 열차 1편성, 실제 작성자 1명이다. **개발 시험용 제안값이며 공식 출동편성이나 이미 측정한 성능은 아니다.** 운전자·승무원은 인력 총수에 포함한다. 실제 기관별 인원은 대상 훈련 명부와 별도로 결속한다.

### 03.4 명시적 제외·후순위

VR/HMD/XR 입력·장치 시험은 포함하지 않는다. 별도 FPS 조작과 RTS 조작을 동시에 완제품으로 만들지 않는다. 자유 건설·경제 경영·공룡·대전 전투는 제외한다. 협업 작성·다중 사용자 훈련·추가 지역·추가 재난은 확장 대상이며 기존 관련 이슈를 무단 삭제하거나 완료 처리하지 않는다. 현장 예측과 무관한 그래픽 장식이 운영 정확도보다 앞서지 않는다.

## 04. 두 사용자 모드와 핵심 여정

### 04.1 공통 규칙

사용자 모드는 정확히 `TUTORIAL`과 `RANDOM_OPERATIONS_LAB` 두 개다. 편집·재생·기관별 정보 보기·물리 계산 프로파일은 모드가 아니라 공통 도구/설정이다. 두 모드는 같은 버전의 공간·권한·업무·자원·보행·물리·로그 코어를 사용한다. 힌트가 켜졌다고 차량이 빨라지거나 자원이 회복되지 않는다.

**주 여정:** 상황 선택 → 운영안 A 실행 → 병목·미충족 조건 확인 → 시점 저장/분기 → 운영안 B 실행 → 동일·변형 조건 비교 → 담당자 선택 → 대본 작성·검토 → 검토된 시나리오를 다시 실행.

### 04.2 TUTORIAL: 실제 훈련·매뉴얼 기반 교육

초기 튜토리얼은 공개 훈련 한 건을 기반으로 하나의 교육 과정으로 제공한다. 안내 실행, 힌트 감소 실행, 복기 평가의 세 단계로 구성한다. 단계별 목표·역할·정보·자원·선행 조건·완료증거를 클릭 가능한 근거 카드로 보여준다. 유효한 여러 부분순서를 허용하며, 한 번의 정해진 클릭 순서만 정답으로 채점하지 않는다.

율현터널 2026-03-11 훈련은 5개 기관·80여 명·고속열차 2대가 참여한 공개 사례다. 전체 대본·세부 편성·작업시간은 보도자료만으로 확인되지 않는다. 부산역 맵에 이 흐름을 재구성하면 ‘율현터널 실물 재현’이 아니라 **해당 공개 훈련에서 영감을 얻은 철도 공조 교육 장면**으로 표시한다. 실제 장소·대본까지 일치한 시점에만 정확 재현 자격을 부여한다. [CASE-YULHYEON]

공개자료 기반 장면과 매뉴얼의 개정판·기관 적용성을 확인한 교육 콘텐츠를 구분한다. 교육용 배포 전 기관 절차 검수와 학습목표 검수를 받는다. 영상의 편집 시간을 실제 업무 소요시간으로 변환하지 않는다.

### 04.3 RANDOM_OPERATIONS_LAB: 조건부 랜덤 운영실험

작성자는 공간, 훈련목표, 사건 계열, 참여기관, 가용자원, 정보 불확실성, 난이도/복잡도를 선택한다. 생성기는 검토된 상황 문법 안에서 조건부 사건 그래프와 초기 상태를 만든다. 작성자는 처음부터 전체 정답 운영안을 제공받지 않고 직접 설계한다. 랜덤 시나리오는 초안 상태로 시작하며 기관 승인으로 자동 승격되지 않는다.

초기 사건 계열은 보안 위협 의심에 따른 운영 제한, 화재·연기 관련 운영, 차량·시설 장애 및 복합 상황으로 나눈다. 각 계열은 검증된 모듈이 준비된 범위에서만 정량 평가한다. 폭발 충격파·구조붕괴·임상 결과가 필요하면 별도 검증 모델 없이는 고정된 조건 또는 미검증 사건 효과로만 표현한다. FDS가 폭발·구조충돌까지 계산한다고 가정하지 않는다. [TECH-FDS-SCOPE]

난이도는 가용성·동시 업무·정보 지연·기관 간 인계 복잡도로 조정한다. 지침 위반을 요구하는 상황을 숨겨 생성하지 않는다. 초기 조건상 추가 지원 없이는 해결할 수 없는 사례는 `ESCALATION_REQUIRED`로 작성자에게 표시한다. 해석·solver 유효범위 밖이면 `UNSUPPORTED`이며 난이도 높은 정상 문제로 위장하지 않는다.

### 04.4 완료 경험

작성자는 ‘무엇이 빨라졌나’뿐 아니라 ‘어떤 역할 충돌이 사라졌고, 어떤 대기를 다른 부담으로 바꿨으며, 어떤 불확실성이 남았나’를 읽을 수 있어야 한다. 결과 선택은 사용자 책임으로 남기고 선택 이유를 저장한다. 원 클릭 로그 → 조건부 운영안 → 훈련 대본의 세 산출물은 별도 버전으로 연결한다.

## 05. RTS × 운영 시뮬레이션 상호작용

### 05.1 조작 원칙

팀/차량 우선 선택과 업무 우선 선택을 모두 제공한다. 지도에서 클릭·다중선택·그룹 저장·대상 우클릭으로 명령을 제안할 수 있고, 업무 카드에서 요구 능력과 가용 후보를 보고 팀을 배정할 수도 있다. 기본 조작 단위는 팀 또는 승무 인력이 결속된 차량이다. 인력을 펼쳐 볼 수 있으나 수백 명의 미세 이동 클릭을 강요하지 않는다.

기관이 섞인 다중선택에서는 권한과 수행 조건이 서로 다르다는 사실을 표시한다. 일부만 실행 가능한 경우 개별 결과를 미리 보여주고 확인받는다. 전체 성공처럼 표시한 뒤 일부를 조용히 누락하지 않는다. 명령 대기열의 순서는 사용자의 의도이지 선행 조건 무시 권한이 아니다.

| 중앙 3D 맵 | 회전·확대·층 선택·지붕/상층 숨김·인물 추적 | 숨긴 벽도 물리·이동 제약은 유지 |

### 05.3 게임성의 원천

재미와 몰입은 클릭 속도나 보너스 능력이 아니라 제한된 자원, 병렬 업무, 불완전한 정보, 기관 간 협조, 여러 유효 대안, 명확한 결과 피드백에서 만든다. 업그레이드 카드로 구조능력·이동속도를 즉시 늘리거나 화재 결과를 보상에 맞춰 바꾸지 않는다. 튜토리얼의 성취 배지는 학습 진행 기록일 뿐 물리모델을 변경하지 않는다.

EMERGENCY의 부문별 선택·현장 지시, Rescue HQ의 가용 자원과 업무 운영, JWE3의 시설 상태·팀 관리·가독성은 UX 참고다. 게임의 권한·자원·응급 행동을 실제 매뉴얼로 수입하지 않는다. [GAME-EMERGENCY, GAME-RESCUEHQ, GAME-JWE3]

### 05.4 UI 마이크로카피 계약

‘이동불가’ 하나 대신 **원인, 영향, 근거, 변경 가능한 입력, 검수 필요 여부**를 표시한다. 예: ‘팀 A의 차량이 다른 업무에 예약되어 있습니다. 예약 해제 예정은 해당 업무 완료 조건에 따릅니다. 다른 가용 팀 선택 또는 기존 배정 취소를 검토하세요.’ 이것은 개선 후보이지 자동 권고 승인이나 실제 기관의 명령이 아니다.

‘지휘소 미준비’를 건물/텐트 설치만으로 판정하지 않는다. 기능 준비와 지휘권 성립을 별도 속성으로 둔다. ‘안전 확인 없음’은 ‘위험이 없음’이 아니며, ‘보고를 화면에 표시함’은 ‘사용자가 인지함’이 아니다.

## 06. 현실 기반 철도 오픈월드 구축

### 06.1 공간 설계

광역 배경, 현장 운영 구역, 업무·이동의 세부 위치를 구분한다. 역사·광장·승강장·객실·지하환승의 13개 기존 root ID를 유지하되 실제 데이터에 맞춰 하위 구역과 연결을 버전 관리한다. 임의 합성 그래프가 실제와 다르면 topologyVersion과 ID migration으로 수정한다. 현재 없는 시설을 편의상 만들어놓고 실물로 표시하지 않는다.

첫 연결에는 외부 도착 노드와 현장 내 업무/인계 위치가 필요하다. 보건소·소방서·병원을 모두 모델링하지 않고 지도 밖 기관과 자원 흐름으로 표현한다. 외부 접근시간이 가정이면 실제 운행시간으로 표시하지 않는다. 임시 운영 배치와 실제 시설 변경안은 별도 레이어다.

### 06.2 네 가지 표현

동일 `physicalAssetId`에 시각 모델, 충돌·보행, 물리 계산 구획/개구, 의미·운영 상태를 연결한다. 시각 LOD나 지붕 숨김이 계산 영역을 삭제해서는 안 된다. 장식물의 외형과 정량 계산의 실제 점유 폭·회전공간·정원·열물성은 분리한다.

기관별 조작 권한은 공간 자체에 묻어넣지 않고 역할·작업의 적용 범위로 연결한다. 접근 가능성과 통행 권한, 작업 가능한 공간, 자원 대기공간은 서로 다르다. 장애·계단·승강기·보조 이동도 경로 비용 하나로 무조건 흡수하지 않는다.

### 06.3 자료에서 Unity까지

**원문/원본 등록 → 대상·시기·해시·단위 확인 → 도면/사진/모델 대조 → 기본 공간 제작 → 필요한 구간 복원·실측 정합 → 표면 정리 → 표현 분리 → FBX/명세 입고 → 운영/물리 결속 → 독립 시험.**

최신 공간복원은 MapAnything를 초기 비교 후보로, COLMAP을 기준선으로 두고 DA3·VGGT-Omega를 동일 입력·제약·수리 비용 조건에서 비교한다. MapAnything는 이미지·카메라/깊이/pose를 조합할 수 있는 복원 프레임워크다. 카메라 Z-depth와 ray-range, pose 방향, 전처리 intrinsic을 명시해야 한다. 가중치와 코드 revision은 실행 전에 고정한다. [TECH-MAPANYTHING, TECH-COLMAP, TECH-DA3, TECH-OMEGA]

AI가 생성한 문·연결부는 실제 관측의 대체가 아니다. 관측되지 않은 영역은 UNKNOWN이며 시각 보완을 해도 provenance는 유지한다. 기준점으로 정합한 뒤 동일 기준점을 독립 검증이라고 재사용하지 않는다. 제어/검증/평가용 관측 세션과 대상 형상을 분리한다.

단위는 m, 시간은 s를 기본으로 하고 현장 좌표·카메라 좌표·Unity 좌표의 변환을 명시한다. 차량은 차량 로컬 좌표를 갖고 승강장과의 연결은 정차/도킹 조건으로 관리한다. 뷰어에 표시됐다는 이유만으로 SKP/FBX 원본을 확보했다고 판단하지 않는다.

### 06.4 기술 결정과 품질

metric PBR 메쉬와 계산용 형상은 필수다. Gaussian 표현은 선택적 정적 배경·재구성 비교용이며 이동·충돌·재조명·열전달까지 해결한다고 가정하지 않는다. 표면 제작은 TSDF/2DGS 등의 후보를 적용 가능성에 맞춰 비교한다. [TECH-TSDF, TECH-2DGS]

가장 중요한 기하 검수는 문·층·연결 누락과 잘못된 이동이다. 평균 표면 오차가 작다고 핵심 경로 결함을 상쇄하지 않는다. 20mm 등의 과거 제안치를 공식 기준으로 승격하지 않는다. 허용오차는 사용자 판단에 미치는 민감도와 실제 측정 불확도에 따라 §16의 QoI 계약에서 사전 고정한다.

## 07. 다기관 운영 모델과 상태 체계

### 07.1 핵심 객체

`Agency`, `Role`, `AuthorityScope`, `Team`, `Person`, `Vehicle`, `Equipment`, `Capability`, `Task`, `Reservation`, `Message`, `Handover`, `OperationalPlan`을 분리한다. 차량을 예약한 상태에서 그 운전자나 장비를 다시 다른 팀에 독립 자원으로 계산하지 않는다. 팀 분리·재조합 때 능력과 남은 자원을 재검사한다.

기관 공조는 외부 요청·접수·가용성 확인·배정·업무 수행·회신의 명시적 흐름이다. 작성자가 전체를 볼 수 있어도 기관 행위자는 전달받은 정보와 자신에게 적용되는 규칙으로 판단한다. 긴급 예외도 출처·적용조건·책임자 없이 모든 제약을 해제하는 만능 버튼이 될 수 없다.

### 07.2 상태와 메시지 수명

업무의 기본 수명은 `REQUESTED → ACKNOWLEDGED → ASSIGNED → RESERVED → STAGED/EN_ROUTE → SETUP → EXECUTING → HANDOVER → COMPLETED`다. 작업유형에 불필요한 단계를 생략할 수 있지만 스키마의 허용 전이표에 명시한다. `WAITING`, `SUSPENDED`, `CANCELLED`, `FAILED`는 원인·후속처리와 함께 기록한다. 업무 종료와 자원의 `RECOVERING/REPLENISHING/AVAILABLE`은 별도 상태다.

메시지는 `CREATED → SENT → DELIVERED → ACKNOWLEDGED → APPLIED`이며 유실·중복·지연·만료가 가능하다. 스냅샷에는 전송 중 메시지와 기관별 belief 상태도 포함한다. 전체 truth와 전달된 정보가 다르면 그 차이를 사용자에게 분석 도구로 보여주되 자동 수정하지 않는다.

## 08. 매뉴얼을 실행 규칙으로 만드는 지식 파이프라인

### 08.1 문서 취득과 현재성

기관 원문·부록·조직체계·훈련 대본·사후평가·실제 관측을 구분한다. 문서명, 발행기관, 판본, 유효기간, 장소/직무 범위, 파일해시, 원문 URL, 쪽/조항, 원본 보유 여부를 등록한다. 최신으로 보이는 웹페이지 날짜를 PDF 개정일로 복사하지 않는다. 법령 시행판·기관 매뉴얼·현장 예외의 충돌은 담당 검수자가 해결한다.

소방 공개 SOP는 선택 절을 확인했으나 개정판 적용성은 미확정이다. 코레일 공개 체계도는 내부 상세 매뉴얼이 아니다. 의료 매뉴얼은 2023-12-20 편집본 안내를 확인했지만 이번 PRD에서 PDF 본문을 취득하지 않았다. 경찰 별표와 부산 풍수해 체계는 해당 철도사고용 지침 전체를 대체하지 않는다. [MAN-SOP, MAN-KORAIL, MAN-MEDICAL, MAN-POLICE, MAN-BUSAN]

### 08.2 규칙 후보 추출·검수

LLM은 원문에서 조건·담당·행동·보고/인계·예외를 후보로 추출한다. 원문 없는 임계값, 역할, 시간, 금지 규칙은 생성하지 않는다. 각 후보에는 source locator와 원문 근거, 적용조건, 해석 이유, 규칙 클래스, 충돌, 검수 상태를 붙인다. 프로그램 제약은 `ENGINEERING_INVARIANT`, 매뉴얼 해석은 `MANUAL_DERIVED`로 구분한다.

검수는 `EXTRACTED → SOURCE_CHECKED → APPLICABILITY_REVIEWED → APPROVED_FOR_TRAINING` 순으로 한다. 기관 교육용 활성 규칙은 승인된 것만 사용한다. 미승인 규칙으로도 개발 fixture를 실행할 수 있지만 학습·기관 검증 결과로 승격하지 않는다. 자동 테스트 통과는 기관 검토를 대체하지 않는다.

### 08.3 개정·영향분석

매뉴얼이 바뀌면 해당 규칙, 튜토리얼, 운영안, 대본, 평가결과를 영향 목록으로 묶는다. 과거 세션은 당시 규칙 버전으로 재생하고, 현재 적용성은 `STALE`로 표시할 수 있다. 기존 시나리오를 새 규칙에 자동 맞춤 수정하지 않고 diff·재검토를 요구한다.

### 08.4 부족한 자료의 처리

대외비 원본을 얻지 못하면 공개 정보로 구성한 부분과 실제 적용성이 미확인인 부분을 분리한다. 원본 제공 대신 비식별 조항·역할표·검수 회신·제한 열람 등 대체 증거를 받을 수 있다. ‘자료가 없으므로 어떤 값이든 사용’과 ‘회신 전 모든 개발 중단’ 모두 금지한다. 영향을 받는 교육 활성화·정량 예측·대본 승인 단계만 보류한다.

## 09. 랜덤 시나리오의 생성·범위·재현성

### 09.1 생성 입력

`ScenarioSpec`은 공간/기관/매뉴얼 버전, 훈련목표, 사건 계열, 가용자원, 외부 접근 모델, 인원 그룹, 정보 전달 조건, 모델 적용영역, 종료 조건을 갖는다. 분포와 상관관계는 근거가 있는 데이터 또는 표시된 설계 가정으로 등록한다. 기본 seed, 생성기 버전과 실제 추출값을 함께 저장한다.

### 09.2 조건부 생성 절차

선택 목표와 사용 가능한 모델을 확인한 뒤 사건 그래프를 구성한다. 공간·자원·시간·인과 관계 제약을 검사하고, 적합한 조합만 실행 후보로 제공한다. 동일 사건에서 서로 관련된 인원·시설 상태·도착 조건을 독립 난수로 무작정 생성하지 않는다. 실패한 생성 시도는 이유를 기록하고 제한된 횟수 후 조건 조정을 요구한다.

생성기가 항상 쉽게 성공하는 조건만 남겨 편향을 만들지 않도록 생성/거부 사유와 분포를 기록한다. 무리한 조합을 제거하는 것과 어려운 정당한 사례를 제거하는 것을 구분한다. 추가지원이 필요한 유형과 지원해도 모델상 판단할 수 없는 유형을 분리한다.

### 09.3 운영안과 외부 조건 분리

작성자가 조정하는 업무 배정·조건부 협조 규칙은 `OperationalPlan`이다. 외부 보고의 지연 법칙, 외부 인원 유입, 사용 가능한 기관 상태는 `ScenarioSpec`이다. 조치로 달라지는 혼잡·정보 생성·후속 도착을 고정 외생 이벤트로 오분류하지 않는다. A/B 비교에서는 동일한 외부 확률 혁신과 조건부 생성 규칙을 결속하되, 사용자 조치가 만든 내생 결과는 각 실행에서 재계산한다.

### 09.4 생성 결과 자격

`FEASIBLE_WITHIN_MODEL`, `ESCALATION_REQUIRED`, `CONFLICTED_INPUT`, `UNSUPPORTED_DOMAIN`을 구분한다. 공조 규칙 검사를 통과한 것이 현장 안전성을 입증하지는 않는다. 유효범위 밖 시나리오를 개발 실험으로 돌릴 수는 있어도 정상 검증 결과와 같은 표로 자동 순위화하지 않는다.

## 10. 시간 제어·스냅샷·분기·운영안 비교

### 10.1 시간 의미

wall clock, simulation time, observedAt, receivedAt, authoredAt을 구분한다. 일시정지는 분석용이며 결과의 시간통계를 왜곡하지 않게 별도 기록한다. 배속은 요청값과 실제 달성값을 표시한다. solver가 따라오지 못하면 과거장을 최신처럼 반복해 표시하지 않고 계산 대기 상태를 표시한다.

### 10.2 스냅샷 범위

스냅샷에는 공간·개체 상태, 기관별 정보, 업무망, 예약·회복/재보급, 전달 중 메시지, 난수 스트림, solver 내부 상태 또는 재시작 가능한 checkpoint, 버전·파일해시가 포함된다. rollback을 지원하지 않는 solver는 가장 가까운 적법 checkpoint부터 재계산한다. 정확 재개가 불가능하면 branch를 새 초기화 실행으로 분류한다.

원본 실행은 불변이다. 분기는 부모 session·sequence·snapshot hash를 참조한다. 동일 이벤트를 재전달해도 외부 효과는 한 번만 적용한다. 취소/실패/분기가 자원을 중복 생성하거나 해제하지 않아야 한다. 사후 작성 메모를 과거 이벤트의 원래 의도로 덮어쓰지 않는다.

### 10.3 비교 설계

한 쌍의 A/B는 같은 맵·규칙·모델·외생 조건 계약으로 시작한다. 그다음 세션·조건을 바꿔 반복 비교한다. 결과는 제약 위반과 다목적 성과를 나눠 제시한다. 허용되지 않는 역할 위반이나 필수 인계 누락을 빠른 종료시간으로 상쇄하지 않는다.

핵심 지표는 업무 누락, 권한 충돌, 자원 중복, 정보 대기, 경로·공간 점유 지연, 인계 완료, 가용자원 부담, 운영 복잡도, 검증된 경우에만 물리 출력이다. Pareto 비지배 대안을 표시하고 사용자 선택 이유를 남긴다. ‘보편 최적’ 대신 ‘시험한 조건과 모델 범위 내 비교’라는 표현을 사용한다.

통계 계획은 선택 전에 고정한다. 초기 30쌍은 계산예산 제안이며 최종 표본수는 변동·목표 정밀도와 사전 정한 종료 규칙으로 정한다. 30회 무사고가 안전성을 입증하지 않는다. 개발 중 좋아 보이는 실행만 골라 비교하지 않으며 선정용 조건과 최종 평가용 조건을 분리한다.

## 11. 시뮬레이션 계산 모델과 SOTA 선정 기준

### 11.1 채택 원칙

최종 제품에는 규칙·공조, 사람 이동, 해당 시나리오의 화재/연기·교통/차량·자원 운영을 결합한다. 모든 재난을 하나의 엔진으로 계산하지 않는다. 최신 학습모델은 강한 후보이지만 검증된 기준 모델보다 정확도가 나쁘거나 상태 복원이 안 되면 채택하지 않는다. **단순 게임용 숫자와 VFX를 현실 계산의 대체로 쓰지 않는 것**이 필수 요구다.

선정 과정은 현상·사용목적·필요 입력 정의 → 기준모델과 최신 후보 실행 → 독립 관측·기준 계산 비교 → 계산 비용·불확도·복구/분기 검사 → 적용영역 승인이다. 모델별 코드는 재현 가능한 commit, 가중치는 revision·해시, 입력과 전처리는 파일 해시로 잠근다.

### 11.2 기술 구성표

| 의료 운영 | 수용·자원·인계의 이벤트 모델 | 분포·민감도 기반 운영 비교 | 임의 체력바·생존율 = 임상 결과 |
| 공간복원 | COLMAP 대조와 실측 정합 | MapAnything·DA3·VGGT-Omega | 신경망 metric 출력 = 현장 실측 |

TAPAAL은 timed/colored/stochastic net과 시뮬레이션·검증 도구를 제공한다. FDS 공식 매뉴얼 페이지에는 6.11.1이 표시되며 저속 화재·열·연기를 대상으로 한다. JuPedSim v1.4.0 공개에는 V3와 WarpDriver가 포함된다. 위 구성은 이번 PRD에서 해당 기능 문서를 확인한 후보이며 설치·현장 실행 합격을 뜻하지 않는다. [TECH-TAPAAL, TECH-FDS, TECH-FDS-SCOPE, TECH-JPS14]

### 11.3 업무·자원 계산

업무망 marking M은 각 팀·개인·장비·정보·권한 토큰의 상태다. 전이 u가 허용되면 `M_next = M + C·u`이며 시간 조건, 적용 rule guard, 기관 권한, 필요한 실제 토큰, 완료 증거를 함께 검사한다. 색상 토큰은 기관/자원 유형을 표현한다. 추상 net과 구현 런타임의 전이 의미를 동일 fixture로 대조한다. 상태공간 제한/timeout은 미검증이지 통과가 아니다. [TECH-TAPAAL]

자원 r의 점유 불변식은 `Σ_j a[j,r]·x[j,t] ≤ C[r,t]`다. 수량 제약과 함께 개인 ID·차량 승무원·장비 소유권의 중복을 검사한다. 예약은 모두 성공하거나 자신이 확보한 부분만 롤백한다. 가용량 변화·취소·지휘 인계·분기에서 보존되어야 한다.

업무 시작시각은 단순 FIFO가 아니라 `start_j = max(요청도착, 선행완료, 정보확인, 자원가용, 공간도달, 적용승인)`이라는 동기 조건의 결과다. 각 항목이 UNKNOWN이면 임의 0으로 채우지 않는다. 실제 소요시간은 작업유형·인력·장비·환경 조건에 대한 근거 있는 분포로 모델링한다. 데이터 없이 모두 지수분포·고정 30초로 가정하지 않는다. 임시 값은 개발 전용으로 구분하고 최종 보정자료와 교체한다.

### 11.4 화재·연기·열 계산

FDS와 같은 검증 대상 solver로 저속 유동의 질량·운동량·종 수송·에너지·복사·표면 열전달을 계산한다. 아래는 데이터 결속을 설명하는 지배식 형태이며 독자적인 간이 solver 명세가 아니다. 실제 수치해법·경계조건은 고정한 solver의 기술문서를 따른다. [TECH-FDS, TECH-FDS-SCOPE]

`∂ρ/∂t + ∇·(ρu) = ṁ'''`

`∂(ρY_k)/∂t + ∇·(ρuY_k) = ∇·(ρD_k∇Y_k) + ω̇_k`

`∂(ρh_s)/∂t + ∇·(ρu h_s) = Dp/Dt + q̇''' − ∇·q'' + Φ`

ρ는 kg/m³, u는 m/s, Y는 무차원 질량분율, h_s는 J/kg, 체적 열원은 W/m³다. 반응·벽·복사·표면에서의 열과 질량 교환을 해당 solver가 정의한 항으로 처리한다. 재료층·형상·개구·환기·열원 입력이 실제/문헌/가정 중 무엇인지 기록한다. 이 식의 표기만으로 현장 정확도나 비선형 안정성을 입증하지 않는다.

핵심 출력 QoI는 선택 위치·시각의 온도, 연기/종 농도, 가시성 관련 수량, 개구 유량 등 사용목적에 필요한 항목으로 제한한다. 실제 위험 임계값은 검토된 기준과 대상·노출 조건 없이 하드코딩하지 않는다. 검증하지 않은 사람의 사망률·압박손상·구조붕괴를 출력하지 않는다.

문·설비 상태 변경은 boundary event로 적용한다. 사전 계산한 서로 다른 장면 영상을 갈아끼우는 방식은 과도상태 연동으로 인정하지 않는다. 사용자가 선택할 수 있는 조작 이력이 학습·검증 범위를 벗어나면 유효범위 검사가 차단한다. FDS+Evac은 지원 중단된 구성을 새 통합 대피 엔진으로 사용하지 않는다. [TECH-FDS-SCOPE]

### 11.5 보행·군중과 층간 이동

권고 경로, 사람의 목표 선택, 국소 보행, 보조 이동, 계단/승강기 운용을 분리한다. 실제 이동 권위는 선택한 보행 엔진 한 곳에만 둔다. Unity NavMesh와 JuPedSim이 같은 사람을 동시에 별도 이동시켜 불일치를 만들지 않게 한다. NavMesh는 후보 경로/표현 보조로 쓰거나 보행 엔진으로 명시 선정한 경우에만 권위를 갖는다.

CFS V3는 방향 회전과 간격 기반 속도 갱신을 분리하며, WarpDriver는 예상 충돌 관련 정보를 사용하는 비교 후보다. 기본값과 샘플 영상은 대상 철도 공간의 보정 데이터가 아니다. 좁은 연결, 합류, 회전, 대향 흐름, 그룹·취약 사용자, 가시성 저하를 별도 시험하고 미지원 현상은 모델 범위 밖으로 표시한다. [TECH-JPS14, TECH-JUPED-V3]

측정 비교에는 위치/속도 시계열, 구역 통과량, 병목 대기 분포, 경로 선택, 안전한 실험에서 얻은 독립 데이터를 사용한다. 2D 단면 통과량의 일관성 검사는 `Q = ∫_crossing ρ_2D(s)·v_n(s) ds`로 사람 수 보존을 확인할 수 있다. 이 집계식이 보행 모델을 대체하지는 않는다. 공공 실험 아카이브를 기본 현상 검증에 사용하고 대상 현장 조건은 별도 검토한다. [TECH-PEDDATA]

### 11.6 교통·차량·의료 운영

도로 접근은 현재 경로·가용성·차량 형태·현지 운행 조건의 어댑터로 처리한다. SUMO 긴급차량 문서의 silent teleport 같은 편의 동작은 정밀모드에서 제거·탐지한다. 교착을 숨겨 해결한 실행은 정상 현장 예측으로 사용하지 않는다. 철도 운행 모델은 경로·운행·정차 등 운영 범위이며 탈선·연결기 파괴·충돌 변형을 자동 계산하지 않는다. [TECH-SUMO, TECH-SUMO-RAIL]

의료는 환자 추적 ID, 가용 인력·차량, 수용정보, 이송·인계·기록의 운영을 우선 다룬다. 임상 판단·처치·중증도 규칙은 의료 검수 후 적용한다. 수용정보의 시각·대기·인계 누락을 검사하며 임의 생존율을 게임 보상으로 사용하지 않는다. [MAN-MEDICAL]

### 11.7 신경 대체모델과 온라인 가속

PhysicsNeMo의 FNO·그래프 기반 모델 등은 가속 후보다. 실제 형상·경계·물성·조작 이력·내부 상태를 입력으로 처리하고 과도상태 안정성을 비교한다. 학습자료는 기준 solver 결과와 관측의 역할을 구분한다. 형상·사건·세션 단위로 학습/보정/검증을 분리한다. 인접 프레임을 독립 holdout처럼 사용하지 않는다. [TECH-PHYSICSNEMO]

surrogate가 기준 solver를 잘 근사한 것과 기준 solver가 현실을 잘 설명하는 것은 별도 평가다. 전역 평균 오차 외에 주요 구역·사건전환 직후·장기 roll-out·보존량·불확도 calibration을 평가한다. 모델 분포 밖 입력에는 예측 신뢰도가 낮다고만 표시하고 계속 승인하지 않는다. reference 계산·재계산 대기 또는 정량 비교 보류로 전환한다.

### 11.8 SOTA 의사결정 산출물

각 모델 선정 기록에는 후보/기준선, 입력 정보의 공정성, 구현·가중치·하드웨어 버전, 실제 실행 명령, 정확도·비용·실패 구간, 검증 데이터 분리, 선정/반려 이유가 있어야 한다. 논문 순위를 자체 성능으로 복사하지 않는다. 유료·승인대기 도구 하나가 전체 독립 개발을 막지 않게 하되, 미실행 대안을 정확한 최종 모델로 가장하지 않는다.

## 12. 다중 엔진 결합·시간·불확도 계약

### 12.1 하나의 물리량에는 하나의 소유자

OperationalKernel은 업무·권한·예약·메시지의 정본, PedestrianAdapter는 선택한 인물 이동의 정본, TrafficAdapter는 외부 차량 이동의 정본, HazardAdapter는 검증된 열·연기장의 정본이다. Unity는 입력과 표현을 담당한다. 결합 경계마다 위치·온도·유량·문 상태의 소유자를 명시한다. 같은 양을 두 엔진이 덮어쓰지 않는다.

### 12.2 이벤트와 연속 계산의 결합

명령은 durable event로 먼저 기록하고 사전조건 검사를 거쳐 승인된 상태 변화만 적용한다. 엔진별 dt는 현상·solver 안정성·수렴 조건에 따라 선택한다. 공통 교환 시점에는 같은 scenario time과 boundary revision을 사용한다. 보간이 필요한 경우 어떤 양을 어떻게 전달했고 보존량 오차가 얼마인지 기록한다. 모든 엔진을 무조건 60Hz로 돌리지 않는다.

문 개폐, 경로 상태 변화, 장비 작동 등 불연속 이벤트에서 경계를 재동기화한다. 비동기 결과에는 계산시각·유효시각·버전이 포함돼야 한다. 오래된 결과를 현재 필드로 덮지 않는다. 동작 지연이 커지면 가상 시간을 제어하거나 평가 자격을 보류하고, 렌더 프레임을 맞추려고 물리 dt를 조용히 키우지 않는다.

FMI는 선택적 교환 수단이다. 어댑터가 FMI나 상태 직렬화를 지원하는지 확인하기 전 이식성·rollback을 보장하지 않는다. 초기에는 명시적 protocol과 프로세스 경계를 사용할 수 있다. [STD-FMI]

### 12.3 불확도와 민감도

측정 불확도, 입력 가정, 수치 오차, 모델 편향, 학습 불확도를 구분한다. 공간·물성·반응시간 등의 불확도는 결과 QoI와 운영안 순위의 변동으로 전파해 비교한다. 결과 차이가 불확도와 비슷하면 ‘우열 불명’으로 표시한다.

정량 비교 예시는 `e = |q_sim − q_obs|`, 허용 판단은 사전 고정한 단위·절대/상대 허용오차·불확도 기준에 따른다. 0에 가까운 관측값의 상대오차 폭증을 피하도록 기준 scale과 절대오차를 함께 정의한다. 기준은 테스트 후 좋은 결과에 맞춰 완화하지 않는다.

### 12.4 현실 기준과 가상 분기의 분리

`REALITY_BASELINE`은 출처가 있는 실제 공간·시설·상태 관측으로 갱신한다. `SCENARIO_BRANCH`는 가상의 사건·운영안으로 변경된다. 게임에서 문을 열었다고 실제 문이 열렸다는 관측을 생성하지 않는다. 실제 대응물을 데이터로 연결하고 지정 빈도·충실도로 갱신한다는 디지털 트윈의 의미를 만족한 범위만 트윈 자격으로 표기한다. [STD-DTC]

현실 관측은 수동·주기적 방식도 가능하나 속성별 cadence·TTL·검수 계약이 있어야 한다. 새로운 실제 관측 revision에 따른 변경 전파와 재검증 증거를 남긴다. 오래된 영상 replay만으로 현재 현실 동기화를 주장하지 않는다.

처음에는 한 PC에서 여러 모듈을 실행할 수 있도록 하며, 대형 solver와 추론은 격리된 프로세스/선택적 외부 계산 노드로 분리할 수 있다. 네트워크가 없어도 저장·실행·수동 편집·과거 근거 조회는 가능한 구성을 우선한다. LLM 호출 실패가 진행 중 운영 상태를 바꾸거나 세션을 잃게 해서는 안 된다.

### 13.2 Unity 기준선과 자산 입고

현재 저장소에서 `6000.3.23f1`을 확인했다. 실제 구현 시작 시 commit·package lock·렌더 파이프라인·플러그인과 시험 OS를 다시 고정한다. 버전 문자열이 확인됐다고 이 PRD의 기능이 구현됐다는 뜻은 아니다. [REPO-UNITY]

렌더 파이프라인은 기존 프로젝트와 후보 에셋의 호환성 시험 후 선정한다. 자동으로 URP/HDRP를 설치하거나 기존 설정을 덮지 않는다. FBX 기본 입고와 명시적 preset을 사용하고 단위·축·스케일·피벗·애니메이션·material·collider를 검증한다. 원본 아카이브의 DLL/실행파일은 승인 없이 실행하지 않는다. [TECH-UNITY-FBX]

### 13.3 로딩·LOD·성능 독립성

초기 작은 현장은 모두 로드해도 된다. 확장 후 구역 단위 additive/비동기 로딩을 사용하되 논리 상태는 별도 수명으로 유지한다. 바닥·충돌·경로·필수 상태가 준비되기 전 진입을 허용하지 않는다. 화면에서 멀어진 인력의 계산을 단순화한다면 그 단순화가 결과에 미치는 오차를 검증한다. 단순히 안 보인다고 사람·예약·메시지를 삭제하지 않는다. [TECH-UNITY-LOAD]

### 13.4 버전·설치·내보내기

배포물에는 실행파일·설정·의존성 버전·콘텐츠 bundle·규칙 승인 상태·모델 qualification·테스트 명세를 포함한다. 서버/solver 시작·정지와 크래시 후 복구를 재현할 수 있어야 한다. 사용자가 선택한 실행형 시나리오는 allowlist 구조 데이터만 포함하고 임의 script·shell·URL fetch를 실행하지 않는다.

기존 화재·군중·열차·서버·음성 코드는 입력/출력·소유권과 실제 완료 상태를 확인한 뒤 재사용한다. 새 엔진 이름이 있다는 이유로 기존 작업을 전면 삭제하지 않는다. 적합하지 않은 부분은 ADR과 단계별 대체 계획으로 마이그레이션한다.

## 14. 플레이 로그 기반 운영안·대본 자동화

### 14.1 자동화가 시작되는 곳

운영 실험 도중 작성자는 중요한 판단을 북마크하고 조건·이유를 적는다. 실행 뒤 AI는 로그의 사실과 병목을 설명하고, 작성자가 선택한 행동을 조건부 운영 규칙 후보로 정리한다. 과거 입력을 시간대로 복사하는 대신 역할·선행 조건·요청·인계·예외를 갖춘 재사용 가능한 운영안을 만든다.

처음부터 플레이가 없는 상황 템플릿을 생성할 수는 있지만 보조 기능이다. 핵심 성공은 **작성자가 시뮬레이션을 통해 운영안을 선택·수정했으며 그 근거가 대본으로 이어지는 것**이다. 자동 생성된 대본이 원인이고 플레이가 확인 절차인 제품으로 방향을 바꾸지 않는다.

### 14.2 기록·추론·권고의 분리

`OBSERVED_IN_RUN`, `AUTHOR_ANNOTATION`, `HYPOTHESIS`, `MANUAL_SUPPORTED_PROPOSAL`, `REVIEWED_INSTRUCTION`을 문장/단계 단위로 구분한다. 실제 수행 문장에는 event ID와 버전을, 사용자 이유에는 annotation 시각을, 권고에는 적용 가능한 source clause와 검수 결정을 연결한다. 로그에 없다는 사실을 미수행으로 단정하지 않는다. 기록 누락 구간은 불확실성으로 표시한다.

시간 차이·예약·경로 존재·상태 결과는 결정적 코드와 solver 기록으로 계산한다. LLM은 숫자를 재계산하거나 성공 상태를 꾸미지 않는다. 선후관계를 인과로 표현하려면 모델 내 반사실 비교 등의 추가 근거와 해당 범위 표기가 필요하다. ‘현실 인과가 입증됐다’는 표현은 별도 현장 증거 없이는 금지한다.

### 14.3 대본 출력

| 출력 | 필수 내용 |
|---|---|
| 종합 상황전개표 | 사건 ID, 시간 또는 발동 조건, 장소, 목적, 분기 |
| 기관·역할·자원표 | 담당·협조·요청/회신 관계, 배정 자원, 적용 가정 |
| 진행자·상황부여 대본 | 상황 내용, 전달 대상, 전달 조건, 진행자 개입 표시 |
| 기관별 행동·보고 문안 | 수행 조건, 확인, 보고/안내 문장, 예외, 근거 |
| 평가·개선표 | 확인할 과업, 관측 근거, 충돌·대기, 수정 사유 |
| 실행형 시나리오 | 같은 ScenarioSpec·OperationalPlan의 구조 데이터 |
| 적용범위 명세 | 맵·매뉴얼·모델·시점·검증영역·불확도·미검증 영역 |

대본의 예정시간과 특정 실행에서 관측된 시간을 다른 필드로 둔다. 고정 시간과 사건 조건을 혼합할 수 있으며, 선행 완료가 필요한 부분을 임의 시각으로 강제하지 않는다. 문서와 실행 데이터는 같은 공통 모델에서 생성한다. 출력은 JSON과 읽기용 Markdown/DOCX를 기본으로 하고, PDF/HWPX 등 기관 양식은 제공 템플릿과 호환성 확인 후 지원한다. xAPI 등 교육 이력 교환은 선택적이며 원시 운영 로그를 대체하지 않는다. [STD-XAPI, REF-MSEL]

### 14.4 리뷰·승인·재실행

초안 편집은 원시 로그를 수정하지 않는다. 승인에는 주체·역할·사유·버전·적용범위·근거·시각이 필요하다. 내용·맵·매뉴얼·모델의 의미 있는 변경은 관련 승인을 만료시키고 diff 검토를 요구한다. `APPROVED_FOR_SIMULATION`, `REVIEWED_FOR_FIELD_EXERCISE`, `AUTHORIZED_FOR_NAMED_USE`를 구분한다. 프로그램 UI에서 누른 승인이 법적·기관적 권한을 자동 부여하지 않는다.

새 실행은 새 session·독립 입력·새 결과를 만든다. 리플레이를 다시 틀거나 사용자 A의 클릭을 자동 반복하는 것을 다른 운영안의 재훈련으로 표시하지 않는다.

### 14.5 AI 평가·실패 처리

모델·prompt·retrieval index·규칙 bundle을 고정해 사실성, 근거 정확성, 미확인 처리, 역할/객체 존재성, 보안과 지연을 평가한다. 문맥은 source revision·기관·사건으로 좁혀 읽는다. 도구 출력·문서·사용자 메모의 지시문은 데이터일 뿐 시스템 권한이 아니다. 비용 상한·호출 timeout·개인정보 반출 정책을 적용한다. 실패 시 수동 작성과 검증된 타임라인은 계속 사용 가능해야 한다.

## 15. AI-native 데이터·온톨로지·추적성 계약

### 15.1 개념 계층

| 계층 | 핵심 개념 | 금지할 혼동 |
|---|---|---|
| 실물·자료 | PhysicalSite, PhysicalAsset, SourceDocument, AcquisitionReceipt, Observation | URL/메타데이터 = 원본 확보 |
| 공간·행동 | SpatialWorld, Zone, Portal, TaskLocation, Capability | 보이는 mesh = 계산상 공간 |
| 기관·운영 | Agency, Team, Role, AuthorityScope, Task, Reservation, Message, Handover | 기능군 = 하나의 실제 지휘조직 |
| 계획·실행 | ScenarioSpec, OperationalPlan, RunSession, Event, Snapshot, Branch | 예정 행동 = 실행 사실 |
| 규칙·의미 | ManualClause, RuleCandidate, ApprovedRule, Applicability, Override | 문장 추출 = 기관 승인 |
| 계산·증거 | ModelRun, ModelQualification, QoIContract, Evidence, ValidationDecision | 코드 통과 = 실물 정확도 |
| 저작·인계 | ResponseDraft, ScriptBundle, ReviewDecision, ChangeSet | 시뮬레이션 승인 = 실제 운영 승인 |

JSON-LD 1.1은 관계를 직렬화하고 PROV-O는 출처·활동·파생을 정렬하는 기반이다. BOT·SOSA/SSN·QUDT는 공간·관측·단위 정렬 후보다. JSON Schema는 필드 구조, SHACL은 그래프 제약에 사용한다. 표준을 도입했다고 의미적 정확성·현장 검증이 자동 확보되지 않는다. [STD-JSONLD, STD-PROV, STD-BOT, STD-SOSA, STD-QUDT, STD-SHACL]

### 15.2 식별자·버전

사람·자원·기관·문·업무·규칙·이벤트에는 안정 ID가 필요하다. 표시 이름 변경이 식별자 변경이 되지 않게 한다. 대상 구분은 site/operator/line/station/vehicleVariant/epoch를 포함한다. 코레일 부산역, 부산교통공사 부산역, 부산진역을 다른 대상으로 기록한다.

실행 버전 벡터는 map, topology, ruleSet, scenario, operationalPlan, operationsKernel, pedestrian, hazard, transport, surrogate, config를 결속한다. 미사용 모듈은 `NOT_APPLICABLE`이며 빈 해시를 정상 적용으로 해석하지 않는다. snapshot에는 adapter별 checkpoint hash와 복원 가능성도 들어간다.

### 15.3 공통 이벤트 필드

`eventId, runId, branchId, sequence, simulationTime, wallTime, actorId, agencyId, commandId, taskId, targetId, eventType, beforeStateHash, afterStateHash, informationRefs, sourceRuleRefs, outcome, reasonCodes, versionVector`를 사용한다. optional 필드는 적용성을 명시하고 0/빈문자열로 결측을 숨기지 않는다. 의료·실사용자 개인정보는 pseudonymous ID와 최소필드로 처리한다.

중복 이벤트 처리, 역순 도착, 재전송, 분기, 취소, 장면 unload, 시스템 복구에서도 기록과 상태가 일치해야 한다. 로그 유실·검사 미실행·원본 미취득을 하나의 성공 상태에 섞지 않는다.

### 15.4 원문→행동→대본 추적

`SourceDocument/Clause → RuleCandidate → ReviewDecision → ApprovedRule → Task/Command → RunEvent → Finding → PlanRevision → ScriptStep → Export` 관계를 유지한다. 각 연결은 실제 ref·hash·scope로 결속한다. 자료 정리용 그래프의 유사도 간선을 작업 선행·권한 승인으로 사용하지 않는다.

### 15.5 첨부 계약의 범위

`requirements.json`은 원자 요구와 우선순위/단계/수용시험의 정본이다. `acceptance-tests.json`은 향후 제품 시험 명세이며 이번에 실행된 제품 결과가 아니다. `rule-catalog.json`은 후보 규칙이며 기관 승인이 아니다. `ontology.jsonld`는 설계 개념·관계의 인스턴스 예시, `schemas/`는 PRD 패키지 구조 검사용이다. 전체 생산 런타임 스키마·API는 EP01에서 확장·검수한다. 단순 참조 유효 검사로 실제 evidence의 진위를 증명할 수는 없다.

## 16. 성공 지표·물리 정확도·현실 적용 수용 기준

### 16.1 핵심 제품 성과

**최우선 성과:** 작성 담당자가 비교 가능한 두 운영안을 실제로 실행하고, 공조·자원·정보·공간상의 차이를 설명하며, 선택한 안을 기관 검토가 가능한 대본으로 전달한다.

| 지표 | 측정 방법 | 초기 목표·상태 |
|---|---|---|
| 사용 가능한 대본까지 총 소요시간 | 같은 난이도의 과제에서 작성·검토·수정시간을 기존 방식과 비교 | 중앙값 30% 절감 가설; 현장 담당자 평가 전 미검증 |
| 핵심 운영 루프 완수 | 상황→A/B 실행→선택→검토→출력까지 무개발자 개입 수행 | 대표 과제 성공률 90% 이상 목표 |
| 근거 추적성 | 출력 문장에서 실제 이벤트·규칙·자료를 열어 확인 | 근거 필수 문장 100% 연결, 잘못된 근거 0 목표 |
| 운영 결함 탐지 | 알려진 중복배정·권한·인계·경로 결함의 정답 집합 | 치명 결함 탐지 누락 0 목표, 오탐률 별도 보고 |
| 기관 검수 수정량 | 의미 변경·사소한 문구수정·미승인 영역 구분 | 이전 작성 방식과 paired 비교; 임의 점수 합산 금지 |
| 교육 이해도 | 튜토리얼 전후와 일정 기간 후 역할·조건 이해 과제 | 사전 정의한 과제 기준 비교; 배지 수를 학습효과로 대체 금지 |

위 숫자는 제안된 제품 목표이지 외부 인증 기준이나 측정된 성능이 아니다. 적격한 작성 담당자·검수자 모집과 비교 과제 설계는 EP00에서 확정한다. 반복 과제의 학습효과는 순서 상쇄/상이한 동등과제로 관리하고, 단순 생성 속도만으로 인력 절감을 주장하지 않는다.

### 16.2 물리·운영 출력 수량 계약

각 QoI 계약은 목적, 위치/대상, 조건영역, 단위, 데이터 출처, calibration/validation split, 오차지표, 허용오차, 불확도, 승인자, 사전 고정 시각과 hash를 갖는다. 값이 없으면 자동 합격하지 않는다.

기하: 핵심 문/층/연결 누락 0, 독립 기준점 residual, 중요한 경로·치수 오차. 보행: 경로·통과량·대기시간 분포·그룹/취약사용자 현상별 적합성. 열·연기: 위치별 시간 이력·유량·온도/종 농도 등 사용목적별 비교. 업무·공조: 권한·예약·정보·인계 불변식과 실제 훈련 수행 데이터/검수. 의료·교통: 운영 수용·접근 조건과 모델 범위에 한정한다.

허용오차는 사용자 판단에 영향을 주는 차이보다 충분히 작고, 관측 자체의 불확도보다 과도하게 정밀하다고 주장하지 않게 정한다. 보정에 쓴 데이터와 독립 검증 데이터를 혼합하지 않는다. 한 조건의 좋은 정확도로 다른 장소·차종·재난까지 일반화하지 않는다. NIST의 검증 방법론은 체계적 V&V와 모델 불확도를 구분하는 참고다. [TECH-VV]

### 16.3 증거의 계층

| 자격 | 필요한 증거 | 허용되는 주장 |
|---|---|---|
| PIPELINE_VERIFIED | 코드·스키마·fixture 실행 | 구현 경로가 명세대로 작동 |
| OPERATIONALLY_CONSISTENT | 역할·정보·자원·상태 전이/일관성 검사 | 명시한 운영 모델 내 모순 점검 |
| MANUAL_ALIGNED | 판본·기관 적용·예외의 전문가 검수 | 지정 매뉴얼과 연결된 훈련 규칙 |
| QUANTITATIVELY_VALIDATED | 독립 실험/현장 자료와 QoI 비교 | 지정 조건·수량의 정량 예측 자격 |
| FIELD_EXERCISE_REVIEWED | 담당기관 도상·시범훈련과 개선 기록 | 지정 훈련에 적용 검토된 운영안 |
| TWIN_QUALIFIED | 실제 대응물·갱신 계약·실제 갱신·모델검증 | 명시한 범위의 동기화된 디지털 트윈 |

자격은 서로 다른 축이다. MANUAL_ALIGNED가 물리 정확도를 대신하지 않고, TWIN_QUALIFIED도 모든 운영안의 안전성을 보증하지 않는다. 사용자에게 단일 녹색 점수로 이 차이를 숨기지 않는다.

### 16.4 출시 구분

연구·교육 시범판은 유효범위와 미승인 조건이 보이는 형태로 제공할 수 있다. **실제 현장 훈련 기획용 권장 결과를 표방하는 버전**은 적용 매뉴얼, 운영 일관성, 판단에 사용한 정량 모델, 해당 현장/조건의 검토를 충족해야 한다. 모든 사고 전체를 승인받아야 한 기능을 사용할 수 있는 구조는 아니며, 출시된 기능의 정확도 요구를 슬쩍 낮추는 구조도 아니다.

대본 승인 주체와 실제 기관의 권한은 별도 확인한다. PRD 작성자나 AI가 기관을 대신해 현장 승인서를 생성할 수 없다.

## 17. 자료·에셋 확보 계획과 실제 확인 상태

### 17.1 확보 수준의 표시

`DISCOVERED`, `PAGE_CHECKED`, `RAW_ACQUIRED`, `FILE_INSPECTED`, `UNITY_IMPORTED`, `MODEL_BOUND`, `DOMAIN_VALIDATED`를 구분한다. 원본의 출처·판본·파일해시·실제 대상·사용 위치·현재 접근 상태를 보존한다. 링크 발견 수와 실제 확보 파일 수를 따로 표시한다.

유료·무료·커뮤니티·Hugging Face 등 후보 검색을 폭넓게 한다. 비용/라이선스 때문에 후보 탐색을 자동 제한하지 않되, 원본 취득·가공·배포와 결제·외부 업로드의 자격은 별도 관리한다. 출처는 저작권 메타데이터만이 아니라 실측/합성, 현재/과거, 부산역/다른 역을 판별하는 기술적 근거다. 접근 통제를 우회하거나 승인 없이 구매·원본 재배포하지 않는다.

### 17.3 핵심 공간 자료

KTX-I는 로컬 아카이브의 바이트 수·SHA256을 이번 PRD에서 다시 확인했다. 165,230,362바이트, SHA256 `099ba06693b50e36f937215d13b73da9b65ba151844f0334cbd3c540c44d7e06`이다. 내부 391파일 등의 분석은 과거 검사 이력이며 이번에 새로 전수 검사하거나 Unity에 임포트한 것으로 쓰지 않는다. [MAT-KTX-I]

승강장 간격 데이터의 소개와 컬럼 타입 차이, 외형 제원과 내부 유효 치수 차이, 상대 기관의 과거 시설 통계와 현재 상태 차이를 그대로 기록한다. 가용 자료의 ‘넓음/좁음’을 밀리미터로 임의 환산하지 않는다. [DAT-PLATFORM-GAP, DAT-METRO1-SPECS]

### 18.3 자원·일정 계획

팀원 수·기관 검수 가능 인원·계산 예산·납기일은 사용자에게 제공되지 않았다. 고정 주수나 ‘몇 주면 완성’은 약속하지 않는다. EP00에서 병렬 가능한 제작·기록·규칙 추출 작업과 기관/데이터 의존작업을 나누고, 실제 throughput 측정 후 일정 baseline을 잡는다.

## 19. AAA급 제품 검수와 반증·재작업 루프

### 19.1 내부 제품 품질 기준

‘AAA’는 예산·업계 인증 명칭이 아니라 아래 축의 내부 수용 목표다. 그래픽 한 축의 고득점으로 운영/근거 결함을 상쇄하지 않는다. 문서 구조 통과를 실제 제품의 통과로 바꾸지 않는다.

| 축 | 필수 검수 |
|---|---|
| 조작·가독성 | 선택·명령·업무상태가 명료하고 층/기관을 바꿔도 맥락 유지 |
| 운영 일관성 | 권한·정보·예약·작업·보고·인계가 같은 이벤트 순서로 연결 |
| 매뉴얼 충실도 | 정확 판본·조건·예외·검수 이력과 실제 UI 동작의 대응 |
| 기하·모델 정확도 | 핵심 공간·모델 QoI와 독립 검증; OOD 탐지 |
| 재현·비교 | 동일 기준 재실행·분기 복원·외생조건 분리·불확도 보고 |
| 저작 결과 | 사실/권고 구분, 문서·실행 데이터 일치, 사람 검토 |
| 시스템 품질 | 크래시 복구·성능·개인정보·콘텐츠 격리·접근성 |
| 현장 활용 | 담당자의 실제 작성 과제·도상/시범 검토와 명시 적용범위 |

### 19.2 자동·수동·외부 검수 분리

schema/단위시험 → 통합·결합시험 → 기준계산·실험 검증 → 사용자 과제 → 기관 검토 순서로 증거를 쌓는다. 모든 계층이 모든 변경마다 전체 재실행될 필요는 없지만 영향 분석과 수용 자격 재계산이 있어야 한다. 작성자·AI가 만든 자기 테스트만으로 독립 물리 검증을 대체하지 않는다.

### 19.3 치명적 반려 조건

없는 자원/객체 사용, 기관 권한의 무단 승격, 필수 인계 누락 은폐, 미관측 상태를 사실로 생성, 모델 범위 밖 수치의 정상 승인, 로그 없는 PASS, 순간이동/렌더 변화로 유리해진 결과, 대본과 실행형 시나리오 불일치, 개인정보·비밀의 무단 외부전송, 사용자 수정으로 원본 실행이 훼손되면 해당 단계 수용을 반려한다.

### 19.4 재작업 절차

동일 입력·버전으로 실패 재현 → 결함 ID와 영향 범위 작성 → 제한된 수정 → 원래 실패 시험과 회귀시험 재실행 → 독립 검수/수용 근거 갱신. 같은 결함이 두 번 재발하거나 필수 입력이 없으면 자동 반복으로 상태를 PASS로 바꾸지 않고 자료·설계 단계로 반환한다. 재시도 횟수/시간/계산 예산은 작업별로 정한다. 한 세션의 무한 루프를 약속하지 않는다.

### 19.5 부정·변이·메타모픽 시험

같은 사람을 차량 두 대에 배정, 권한 인계 이전의 지시, 기관에 전달되지 않은 정보의 사용, 잘못된 단위, 다른 맵의 객체 ID, 위조 출처, seed만 같은 다른 외생조건, 누락 checkpoint, 결과가 좋아지는 물리 shortcut을 의도적으로 입력한다. 모드 안내·카메라·LOD·프레임이 결과를 바꾸지 않는지도 확인한다.

제품 인수시험의 상세 ID와 Given/When/Then은 `contracts/acceptance-tests.json`에 있으며 모든 제품 결과는 최초 `NOT_RUN`이다. PRD 패키지에 대한 로컬 구조 검사와 제품 인수시험을 구분한다.

### 20.2 접근성·한국어 UX

한국어 기본 용어집, 키보드 조작, 확대 가능한 글자, 색 이외의 상태 표식, 다층 공간의 선택 명료성, 읽을 수 있는 시간/단위 표기를 제공한다. 소방·경찰·철도·의료의 원 용어와 게임 설명을 함께 볼 수 있도록 한다. 동일 표시 이름의 다른 기관·역·차량은 소속과 식별자를 같이 표시한다.

### 20.3 보안·개인정보·자료 취급

연구 자료도 source/access/use를 기록하고 원본과 공개용 파생본을 분리한다. 실제 사람·환자·직원 정보는 불필요하게 수집하지 않는다. 익명 세션 ID를 기본으로 하고 음성/자유 메모/개인정보는 명시 동의·반출 정책을 따른다. 실제 환자 진료 정보를 기본 학습 데이터로 쓰지 않는다.

raw/log/대본은 권한에 따라 접근하고 export 전 비밀·개인정보 필터와 사람 확인을 적용한다. 보관기간은 기관/프로젝트 정책으로 설정하며 무기한 저장을 기본으로 하지 않는다. 첨부 아카이브의 path traversal·실행파일·macro를 검사한다. 외부 문서의 지시로 시스템 권한·파일·승인 상태를 변경하지 않는다.

### 20.4 승인·감사·회귀

승인과 수정에는 audit trail을 남기고 원본/출처 hash를 보존한다. 중요 변경은 인수시험과 source version 관계로 추적한다. 누가 무엇을 승인할 수 있는지는 애플리케이션 역할과 실제 기관 위임을 모두 확인한다. 프로토타입 계정의 ‘관리자’ 권한이 현장 사용 승인 권한은 아니다.

## 22. 승인·완료 정의와 개발 AI 인계

이 PRD의 최종 승인 대상은 제품 범위, 두 모드, 운영 UX, 사고별 정량 검증 수준, 현장 활용 자격, 일정/예산과 기관 검수 계획이다. 사용자 요구의 방향은 대화에서 주어졌으나 모든 제안 수치·기술 후보·일정 결정이 기관 승인된 것은 아니다.

**제품 완료는 다음 모두를 갖춘 지정 범위의 릴리스다.** 작성 담당자가 실제 맵에서 기관·자원을 운영한다. 매뉴얼 근거와 예외가 동작한다. 같은 코어의 튜토리얼·랜덤 모드에서 새 운영안을 시험한다. 분기·비교가 같은 조건을 보존한다. 판단에 사용하는 물리·운영 출력이 명시된 검증 범위를 갖는다. 로그→운영안→대본→실행형 데이터가 연결된다. 사람이 검토하고 새 실행이 가능하다. 기관 검토와 적용 한계가 함께 전달된다.

초기 실행 지시는 EP00의 범위·소스·입력 계약 확인 후, EP01/02의 운영 코어와 EP03의 공간 제작을 분리해 착수하는 것이다. 없는 현장 자료·검수자를 있다고 가정하지 않는다. 합성 fixture·실제 원본·승인 규칙·정량 증거는 서로 다른 자격으로 유지한다. 읽기용 문서나 모델의 최신 이름을 구현 성공으로 승격하지 않는다.

**이번 전달:** PRD 본문·원자 요구·인수시험·원문 등록부·에셋 후보·온톨로지·개발 AI packet·문서 검수 기록. 제품 코드·물리실행·기관 승인·GitHub 변경은 수행하지 않았다.

## 부록 A. 요구사항·인수시험·레퍼런스 찾아보기

`REQUIREMENTS.md`는 모든 원자 요구사항과 인수시험 ID를 정리한다. `TRACEABILITY.md`는 UR-01–UR-22가 어떤 요구·작업·시험으로 연결되는지 제공한다. `SOURCES.md`는 실제 원문 URL·확인 수준·사용 범위·한계를 담는다. `contracts/`의 JSON은 같은 내용을 기계가 읽는 표현이며 제품의 완료 상태는 별도 evidence에 기록한다.

문서에 있는 [MAN-…], [TECH-…], [AST-…], [CASE-…], [STD-…], [MAT-…], [DAT-…]는 `SOURCES.md`와 `contracts/sources.json`의 source ID다. 확인한 웹페이지와 원본 파일, 이번 재확인과 이전 이력은 분리돼 있다. 이 PRD는 자료 전체를 새로 취득했다고 주장하지 않는다.
