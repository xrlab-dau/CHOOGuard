## 0. 공개 범위와 비공개 부록

이 저장소는 **public**이고 이 문서도 public이다. 독립 검토(safety SAF-1)가 지적한 대로, 보호 규칙 식별자·우회 경로의 구체적 조합·대응 인력 규모를 한 문서에 모으면 결함이 고쳐지기 전까지 공격자에게 지도가 된다.

따라서 이 공개본은 **결함의 존재·심각도·결정 대상**만 기록하고 아래 항목을 제외했다.

**주의: 비공개 부록은 아직 존재하지 않는다.** 2라운드 검토 세 관점이 모두 "부록이 없는데 이관했다고 서술한 것"을 지적했다. 정확한 상태는 **공개본에서 제외했을 뿐이며, 저장소 밖 TEAM_INTERNAL 기록은 PM이 생성·유지해야 한다**는 것이다. 부록이 만들어지기 전까지 아래 항목의 권위 있는 사본은 어디에도 없다.

- ruleset 식별자와 각 규칙의 전체 파라미터 표
- 우회 경로의 정확한 유형·모드·적용 조건
- 팀 구성원·초대 수치와 개인 매핑
- 재조회 명령의 원문 출력

PM과 저장소 관리자는 비공개 부록으로 결정하고, 이 문서에는 결정 결과만 비민감 형태로 남긴다. 결함이 해소된 뒤에는 공개본에 상세를 복원해도 된다.

## 3. 보호 경로·리드 소유권 변경안

### 3.1 POLICY_GLOBS와 CODEOWNERS의 범위 불일치

`verify_toolchain.py`의 `POLICY_GLOBS`는 **14개 패턴**이고 `CODEOWNERS`의 리드 규칙은 8개 경로다. (초판은 15개로 잘못 적었다 — 독립 검토 spec SPC-2, adversarial ADV-2.) 두 목록이 어긋난다.

**POLICY_GLOBS에 있으나 리드 규칙이 없는 경로**

| 경로 | 성격 |
|---|---|
| `.pi/` 하위 5개 패턴 | 에이전트 실행 정책 |
| `.specify/memory/constitution.md` | 헌법 |
| `docs/adr/*.md` | 승인된 결정 기록 |
| `scripts/ci/*.py` | **정책 검사기 자신** |
| `scripts/bootstrap/*` | 부트스트랩·검증기 |
| `tools/research/{pyproject.toml,uv.lock}` | 공급망 lock |

`docs/evidence/`(`RECEIPT_ROOT`)는 **양쪽 어디에도 없다.**

**리드 규칙이 있으나 POLICY_GLOBS에 없는 경로:** `/SECURITY.md`, `/Packages/`, `/ProjectSettings/`, `/schemas/`, `/Assets/ChooGuard/Runtime/{Scoring,Safety}/`.

### 3.2 변경안

**변경안 A — 리드 규칙 추가.** CODEOWNERS는 **마지막 일치 규칙**이 이기므로 파일 끝에 둔다. 대상: `.pi/`, `.specify/memory/`, `docs/adr/`, `docs/evidence/`, `docs/reviews/`, `scripts/ci/`, `scripts/bootstrap/`, `tools/research/`의 lock 파일.

주석은 "POLICY_GLOBS와 범위를 맞춘다"가 아니라 **"POLICY_GLOBS 및 추가 증거·검토 경로를 리드 규칙으로 보호한다"**로 적는다. `docs/evidence/`와 `docs/reviews/`는 POLICY_GLOBS에 없기 때문이다(독립 검토 spec SPC-3).

**변경안 B — 개인 로그인을 팀으로 교체(G-08).** 전용 리드 팀을 만들어 교체하면 공개 매핑 문제가 해소되고 인원 변동에도 규칙이 유지된다. 팀 생성·구성원 지정은 별도 승인이다.

**변경안 C — 보류.** 초판은 `docs/evidence/`를 POLICY_GLOBS에서 제외하고 CODEOWNERS로만 통제하자고 제안했다. **이 제안은 보류한다.** CODEOWNERS는 append-only·삭제 금지·과거 영수증 불변성을 강제하지 못하며, ADR 0003이 요구하는 증거 무결성을 대체할 수 없다(독립 검토 safety SAF-5). 증거는 별도 manifest 또는 해시 체인과 삭제·수정 탐지로 다루고, 그 보상 통제가 검증되기 전에는 어느 쪽도 승인하지 않는다.

### 3.3 적용 순서 — 선제 등록이 핵심이다

`.pi/`·`.specify/`·`docs/evidence/`는 PM 승인 대기로 미추적이다. 초판은 이를 두고 "규칙을 넣어도 무효"라고 적었는데 **오해를 부르는 서술이었다**(독립 검토 safety SAF-7).

정확히는 이렇다. CODEOWNERS 규칙이 **기준 브랜치에 먼저 있으면, 그 경로의 파일을 처음 추가하는 PR부터 리드 검토가 걸린다.** 따라서 선제 등록은 무의미한 것이 아니라 **보호 대상을 커밋하기 전에 반드시 선행해야 하는 통제**다. 순서는 (1) CODEOWNERS 변경 PR 병합·검증 → (2) 보호 경로 파일 커밋이다. 순서를 뒤집으면 첫 커밋이 리드 검토 없이 들어간다.

## 4. 개별 검토 항목

### 4.1 비밀 탐지·push protection (G-02)

- 저장소는 public이고 조직 플랜은 free다. **public 저장소에서 secret scanning과 push protection은 추가 비용 없이 쓸 수 있다.**
- 다만 **기능별로 권한이 다르다.** 비공급자 패턴 탐지와 유효성 검사는 별도 상위 권한이 필요하며 public 가시성·free 플랜만으로 성립하지 않는다. 초판은 이를 묶어 "가용성 조건 해소"라고 적었다(독립 검토 adversarial ADV-1). **기본 두 기능만 조건이 해소됐고 나머지는 기능별 확인이 필요하다.**
- 위험: `scripts/ci/repository_policy.py`는 **커밋된 뒤에** 일부 패턴을 잡는 사후 검사이며 push protection처럼 푸시 자체를 막지 못한다.
- **제안: push protection 포함 활성화.** 설정 변경은 별도 승인이다.

### 4.2 병합 방식 (G-03)

§5.2 참조. 저장소 수준 rebase 허용은 보호 브랜치에서 ruleset이 우선하므로 실효가 없다. 명확성을 위해 비활성화를 제안하되 main용 merge commit은 유지한다.

### 4.3 브랜치 보존 (G-04)

자동 삭제는 병합된 브랜치만 지우고 보호 규칙이 기본 브랜치를 막는다. 다만 작업 그래프 §3.2가 "한 노드 한 브랜치 한 PR"을 요구하므로 **보존 기간 정책을 먼저 정한 뒤** 결정한다. 브랜치 자체가 추적 증거인 작업에는 예외가 필요하다.

### 4.4 Dependabot PR (G-05)

5건 모두 GitHub Actions 메이저 버전 상향이며 `.github/workflows/`는 리드 소유이자 POLICY_GLOBS 해시 대상이다. **일괄 병합하지 않는다.** 각 PR은 major 호환성·필수 검사 통과·리드 승인을 개별 확인한다. 보안 업데이트 활성화는 별도 결정이며, 활성화해도 자동 병합은 되지 않는다.

### 4.5 잔류 브랜치 (G-07)

`main-1`의 고유 커밋 `c3db2e9`(README 제목·서식)는 PR #6이 **병합되지 않고 닫히며** 남았다. 이후 PR #8이 대체했을 가능성이 높으나 바이트 대조는 하지 않았다. **삭제 전 내용이 현재 README에 반영됐는지 사람이 확인한다.**

### 4.6 브랜치 업데이트·자동 병합 설정

- 관측: 브랜치 업데이트 허용과 자동 병합이 모두 꺼져 있다.
- 자동 병합이 꺼져 있는 것은 이 프로젝트의 승인 요구와 맞다. Dependabot 보안 업데이트를 켜도 자동 병합되지 않는 근거다.
- 브랜치 업데이트 허용이 꺼져 있으면 base가 앞선 PR을 UI에서 갱신할 수 없어 작성자가 로컬에서 rebase·merge해야 한다. 보호 브랜치의 병합 방식 제한과 상호작용하므로 의도된 선택인지 확인이 필요하다.
- **제안: 두 설정 모두 현 상태 유지를 기본값으로 하되 의도를 명시적으로 기록한다.** 초판은 이 항목을 §6 결정 목록에만 두고 본문 근거 절이 없었다(2라운드 spec R2-SPC-2, adversarial R2-ADV-5).

## 5. 재확인에서 정밀화된 항목

감사 v1.1의 기존 발견을 서버 설정 수준에서 정밀화한 것과, 새로 드러난 강제 격차를 구분한다. 초판은 이를 모두 "신규 발견"이라 적었으나 과했다(독립 검토 adversarial ADV-6).

### 5.1 상시 우회 경로 (G-01·G-11의 정밀화, HIGH)

승인 1건·CODEOWNER 검토·필수 검사를 담은 **유일한 보호 ruleset에 상시 우회 주체가 등록돼 있다.** 해당 주체는 PR 경로에서 그 규칙들을 우회해 병합할 수 있다.

**감사 G-11("PR 작성자는 자기 PR을 승인할 수 없고 독립 팀 검토자가 필요하다")이 서버 측에서 강제되지 않는다.** 명세 001 FR-004의 리드 소유권 검사와 ADR 0003의 독립 검토 요구도 같은 이유로 강제되지 않는다.

초판은 "우회 주체 제거 또는 모드 축소"를 제안했으나 **현재 모드가 이미 가장 좁은 값이라 축소할 여지가 없다**(독립 검토 adversarial ADV-5). 실행 가능한 선택지는 **제거** 또는 **ruleset 재설계**뿐이다.

초판은 또 "제거 시 긴급 복구 경로가 사라진다"를 이유로 결정을 유보했다. 독립 검토 safety SAF-2가 이를 **HIGH 위험의 무기한 방치**로 지적했고 타당하다. 정정한 제안은 다음과 같다.

- **기본값은 상시 우회 제거다.** 복구 필요성이 상시 우회를 정당화하지 못한다.
- 복구는 별도 break-glass 절차로 설계한다: 복수 승인, 짧은 만료, 사후 감사 기록.
- **결정 전까지 이 ruleset이 독립 검토를 강제한다고 주장하지 않는다.** 결정 기한을 정하고, 그때까지 병합은 사람이 독립 검토를 확인한 뒤에만 수행한다.

상세 파라미터와 주체 식별은 비공개 부록에 둔다.

### 5.2 ruleset 이름과 실제 규칙의 불일치 (G-03의 정밀화, MEDIUM)

- develop 대상 ruleset의 이름은 squash 전용을 표방하지만 **실제 규칙에 병합 방식 항목이 없다.**
- develop이 squash 전용으로 동작하는 것은 **두 규칙의 결합** 때문이다. 공유 ruleset의 병합 방식 제한이 rebase를 배제하고, develop ruleset의 선형 이력 요구가 merge commit을 배제한다. **선형 이력 요구만으로는 rebase가 허용되므로** 어느 한쪽이 빠지면 즉시 열린다(독립 검토 adversarial 지적).
- main에는 PR 규칙이 둘 걸려 있고 GitHub는 규칙을 합산하되 충돌 시 가장 제한적인 값을 적용한다.

**초판의 "중복 규칙 정리는 실효 동작을 바꾸지 않는다"는 틀렸다.** main 전용 규칙에는 공유 규칙에 없는 **추가 승인 요구**와 **더 좁은 병합 방식 제한**이 들어 있다. 제안대로 지웠으면 두 통제가 사라졌을 것이다(독립 검토 safety SAF-4).

**정정한 제안:** 규칙을 지우기 전에 변경 전후 모든 PR 규칙 필드의 실효 정책 비교표를 만들고(비공개 부록), 추가 승인과 병합 방식 제한을 보존하는 대체 규칙을 승인·시험한 뒤에만 정리한다.

### 5.3 강제되지 않는 게이트 (신규, HIGH)

**병합을 실제로 막는 필수 검사는 하나뿐이다.** 그런데 PR 위험 분류 워크플로는 위험도와 변경 영역에 따라 `Reconstruction CI`, `Unity 테스트`, `area-owner review`, `lead review`, `Windows build and physical-headset release gate`를 "필수"로 제시한다. **이 목록은 PR 댓글 본문 텍스트일 뿐 어떤 status check도 만들지 않는다.** 해당 워크플로 자신도 필수 검사가 아니다.

즉 **main 릴리스에 리드 검토와 Windows·실기 게이트가 요구된다고 표시되지만 아무것도 막지 않는다.** 문서·댓글이 강제를 구현한 것이 아니다.

**제안:** "필수"와 "권고"를 표기부터 분리하고, 실제 강제가 필요한 항목은 status check와 ruleset으로 구현한다. 경로 필터가 있는 워크플로를 필수로 지정하면 해당 경로가 없는 PR이 영구 대기하므로 skip job 패턴을 함께 설계한다.

### 5.4 기본 브랜치에 묶인 보호 (신규, MEDIUM)

핵심 ruleset 둘이 develop을 명시적으로 지정하지 않고 **기본 브랜치 참조**로 대상을 잡는다. 기본 브랜치를 바꾸면 develop 보호가 함께 이동해 **develop이 보호를 잃는다.**

**제안:** develop을 명시 지정하거나, 기본 브랜치 변경을 별도 HIGH 승인과 ruleset 재검증 없이는 수행할 수 없도록 통제한다.

### 5.5 자기 자신을 통과시키는 게이트 (신규, HIGH)

유일한 필수 검사는 **PR head의 `scripts/ci/` 검사기와 그 테스트를 그대로 실행한다.** 따라서 검사기와 테스트를 함께 완화하는 PR은 스스로를 PASS시킨다. `scripts/ci/`에 리드 규칙이 없다는 §3.1의 문제와 결합하면 리드 승인 없이 통제를 해제할 수 있다.

**제안:** `scripts/ci/**`와 그 테스트를 독립 HIGH 차단 항목으로 두고 리드 CODEOWNER 보호를 **선행** 적용한다. 가능하면 검증기 변경 PR에서 기준 브랜치의 신뢰된 검사기를 함께 실행해 self-modification을 탐지한다.

### 5.6 권한 있는 워크플로의 향후 변경 위험 (신규, MEDIUM)

PR 위험 분류 워크플로는 fork PR에서도 base 저장소 권한으로 실행되며 PR·이슈 쓰기 권한을 가진다. **현재는 PR 코드를 체크아웃하거나 실행하지 않아 안전하다**(job 이름도 그 사실을 밝힌다). 그러나 나중에 체크아웃이 추가되면 쓰기 토큰이 걸린 임의 코드 실행이 된다.

**제안:** 현 상태 유지의 근거와 신뢰 경계를 문서화하고, **향후 이 워크플로에 PR head 체크아웃을 추가하지 않는다는 조건**을 명시한다. 쓰기 권한 최소화도 함께 검토한다.

## 7. 독립 검토 결과

2026-09-06, 작성 제공자(anthropic)와 **다른 제공자(OpenAI gpt-5.x 계열)**로 필수 3관점 독립 검토를 수행했다.

| 관점 | 판정 | 지적 |
|---|---|---|
| spec | `changes_required` | 4건 |
| safety | `changes_required` | 7건 |
| adversarial | `changes_required` | 8건 |

**세 관점 모두 승인하지 않았다. R-03은 `cannot_proceed`를 유지한다.** 이 v1.1 개정은 지적을 반영한 것이며 개정본 재검토는 수행되지 않았다.

검토가 확인해 준 것: manifest 해시 일치, G-01~G-11 재확인에 누락 없음, 서버 관측값 일치, 개인 로그인·주체 신원 미노출, `main-1` 관측 정확, 상시 우회 경로의 핵심 해석과 "가장 제한적인 값 적용"은 문서대로 타당함.

기각한 지적 1건: `scripts/bootstrap` 추적 파일이 5개라는 주장(adversarial). `git ls-files` 결과는 4개이며 spec 관점도 4로 셌다.

**수용 기준 2번은 미충족이다.** "변경안을 작성하고 PM 결정을 받는다" 중 결정을 아직 받지 않았다(독립 검토 spec SPC-1). R-03은 **변경안 초안·PM 결정 대기** 상태다.

## 7.1 2라운드 검토 결과

1라운드와 다른 모델 배정으로 3관점 재검토를 수행했다.

| 관점 | 판정 | 1라운드 종결 | 신규 |
|---|---|---|---|
| spec | `cannot_proceed` | 3 종결 / 1 open | 3 |
| safety | `changes_required` | **0 종결** / 4 부분 / 3 open | 4 |
| adversarial | `changes_required` | 5 종결 / 3 부분 | 5 |

**세 관점 모두 미승인이다.**

**safety 관점의 완전 종결이 0건이라는 사실이 핵심이다.** 문서 품질 문제가 아니다. 남은 항목이 보호 규칙 변경, 상시 우회 제거, 필수 검사 승격, 비공개 부록 생성이며 전부 **PM 결정과 실제 GitHub 설정 변경**을 요구한다. 문서를 다시 고쳐도 "제안은 아직 구현되지 않았다"는 판정은 바뀌지 않는다.

이 v1.1 개정은 2라운드가 지적한 **사실 오류와 서술 문제만** 고쳤다. G-02 통제 상태 표현, 비공개 부록의 실제 상태, §6 결정 항목의 본문 근거가 그것이다. 설정 의존 항목은 손대지 않았다.

**따라서 R-03에는 3라운드를 적용하지 않는다.** 계약상 남은 마지막 라운드를 문서 재검토에 쓰면 아무것도 닫지 못한 채 소진된다. PM 결정과 승인된 설정 변경이 끝난 뒤 그 결과를 대상으로 검토하는 것이 맞다. 이 순서는 PM 결정 사항이다.

2라운드가 지적했으나 이 개정에서 **해소하지 못한 것**: 축약으로 훼손된 검증 가능성(safety는 축약 강화를, spec·adversarial은 증거 복원을 요구해 방향이 상충한다. 비공개 부록 생성이 선행되어야 양쪽을 만족한다), 상시 우회 제거의 실제 기한·책임자, §5의 모든 설정 변경 제안.

## 8. 잔여 게이트

- 이 문서는 GitHub 설정·권한·CODEOWNERS를 **변경하지 않았다.** 조회는 모두 읽기 전용이었다.
- 승인된 변경은 별도 PR로 수행하고 마지막 일치 CODEOWNERS 검사·필수 CI·독립 팀 검토 증거로 확인한다.
- 서버 관측은 재현 불가능한 시점 기록이다. **적용 직전 재조회한다.**
- 개정본에 대한 다른 제공자의 독립 재검토가 미완료다.
