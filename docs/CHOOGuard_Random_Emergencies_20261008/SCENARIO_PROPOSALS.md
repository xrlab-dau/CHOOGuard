# 부산역 건물 안에서 합성되는 비상상황 확장 제안

작성일: 2026-10-08. 이 문서는 현재 소스에서 확인한 동작과 추가 구현 제안을 구분한다. 아래 44개는 객체의 변화가 조합되었을 때 나타날 수 있는 **결과 예시**이며, 구현할 사건 목록·시나리오 ID·선택 테이블이 아니다. 번호는 문서 검토용이다.

이번 변경에서 실내 원인 검사, 원인 객체별 독립 발생, 개별 매달린 객체 판단, 현재 실내 객체 집계의 JEV 입력을 코드에 반영했다. **전시 경보·강우 입력·외부 조건 전달·범용 객체 능력의 신규 어댑터와 44개 예시 전체를 구현한 것은 아니다.** 아래 코드 반영 사실과 향후 제안을 구분하며, 이 문서에는 실제 플레이 및 JEV 합성 실행 검증 결과를 기록하지 않았다.

사용자가 말한 ‘전시상황’은 여기서는 **전시(戰時), 즉 전쟁 중 민간인 보호 상황**으로 해석했다. 전시회·행사라는 뜻이었다면 같은 군중·안내·설비 모델에 행사 인원 상태를 추가할 수 있다. 전시·보안·테러 관련 내용은 관찰 가능한 이상과 시민 보호 목표까지만 다룬다.

## 1. 어떤 무작위성이 필요한가

목표는 매번 다른 원인 객체, 시작 시각, 변화 크기, 목격자, 발견 순서, 영향 범위, 파생 변화, 대응 결과가 나오는 것이다. 무조건 아무 사건이나 나오는 균등 난수보다 **현재 세계에서 가능한 일이 JEV의 임박도 판단에 따라 시간 속에서 일어나는 방식**이 맞다. 같은 보조배터리 과열도 빈 좌석 근처라면 짧은 연기와 조기 신고로 끝나고, 혼잡·불량 감지기·셔터 동작·늦은 발견이 겹치면 의료·대피·우회 문제가 함께 생길 수 있다. 이러한 조합을 대본으로 미리 작성하지 않는다.

건물 안 발생 조건은 발생 원인 객체와 실제 적용 위치에 모두 적용한다. 실내 출입문 안쪽, 실내 맞이방, 실내 계단·에스컬레이터, 실내 점포, 등록된 실내 설비가 대상이다. 광장, 외부 도로, 옥외 선로, 열차 객실은 건물 내부라고 자동 해석하지 않는다. 대피 완료 지점은 외부에 있을 수 있지만 새 사건의 원인이 그곳에서 시작하지 않게 한다. 지진·정전처럼 역 전체가 원인인 기존 예외도 실제 피해·상호작용은 실내 등록 객체에서만 전개하도록 제한한다.

이 문서의 ‘출입구’, ‘창’, ‘통로’, ‘점포’, ‘대기 장소’는 **게임맵에서 확인하고 실내로 등록한 객체·공간**을 뜻한다. 실제 부산역에 특정 창고·대피시설·수신기·의료시설이 그 위치에 있다고 주장하지 않는다. 필요한 연결이나 원인 객체가 등록되지 않은 예시는 후보가 되지 않는다.

## 2. 현재 코드가 이미 제공하는 기반과 제약

직접 확인한 기반은 다음과 같다.

- [StationEquipment.cs](../../Assets/ChooGuard/App/Fps/Equipment/StationEquipment.cs)는 배치된 설비의 `Id`, `Kind`, `Label`, `Zone`, `Data`, `State`와 상태 변화 이벤트를 제공한다. 활성 객체만 레지스트리에 들어간다.
- [IncidentDirector.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.cs)의 `Transition`, `Bound`, `Each`, `Recheck`는 특정 실재 객체에 후보를 묶고 실행 직전 다시 확인하는 구조다. 역무실 보고, 방송, 직접 대피 안내, 접근 통제, 기관 출동 및 현장 인계도 이 파일에서 확인했다.
- 이번 변경의 [IncidentDirector.Building.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.Building.cs)와 [StationBuilding.cs](../../Assets/ChooGuard/App/Fps/Emergency/StationBuilding.cs)는 실제 건물 내부 여부를 검사한다. `Bound`/`Each`에서 `IndoorSubject`로 원인을 검사하고 재확인 때도 다시 적용하며, 승객의 `InTrain` 상태와 열차·승강장·선로 원인은 대상에서 제외한다. 실내 구역 이름만 붙여 외부 원인을 통과시키지 않는다.
- [IncidentDirector.Compose.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.Compose.cs)는 원인과 전개 후보를 JEV에 묻고 임박도를 연속시간 위험률로 변환한다. 1초 박동과 상황 변화 감시, 평가 갱신·만료, 요청 예산, 디렉터 전용 난수열이 있다. JEV가 꺼져 있거나 키가 없으면 비상상황을 대신 만드는 로컬 합성기는 없다.
- 이번 변경의 [JevWorldInventory.cs](../../Assets/ChooGuard/App/Fps/Emergency/JevWorldInventory.cs)는 활성 실내 승객·수하물·배터리 보유·설비 종류와 상태·이동 설비·남은 매달린 객체를 읽어 집계하고, `Focus.world_objects`로 JEV에 보낸다. 합성 조건과 같은 실내 판정을 쓰며 최대 게임 1초마다 갱신한다. 이 집계는 판단 맥락이며, 없는 객체를 생성하거나 아직 구현하지 않은 원인을 실행시키는 능력은 아니다.
- [IncidentDirector.Casualty.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.Casualty.cs)는 쓰러짐·경련·가슴 통증·호흡 곤란·저혈당 양상, 계단 추락, 에스컬레이터 넘어짐·끼임·가방 낙하를 제공한다. AED를 환자 곁에 놓고 구급대에 인계하는 행동은 확인했으며, 이것을 플레이어의 상세 의료 처치 구현으로 확대 해석하지 않는다.
- [IncidentDirector.Fire.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.Fire.cs), [IncidentDirector.KitchenGas.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.KitchenGas.cs), [IncidentDirector.ElectricPlaza.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.ElectricPlaza.cs)는 승객 배터리·실재 쓰레기통·주방 조리기기·가스 연결부·전기설비 원인을 제공한다. 전원·밸브와 기존 설비 상호작용은 해당 객체와 연결이 있을 때만 사용할 수 있다.
- [IncidentDirector.Facility.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.Facility.cs), [IncidentDirector.FireSafety.Sprinklers.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.FireSafety.Sprinklers.cs), [IncidentDirector.FireSafety.Shutters.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.FireSafety.Shutters.cs)는 지진, 낙하물, 승강기 정지, 정전, 누수, 셔터와 실재 소방설비 연결을 제공한다.
- [IncidentDirector.Security.cs](../../Assets/ChooGuard/App/Fps/Emergency/IncidentDirector.Security.cs)는 방치 가방, 난동, 협박 전화, 미확인 가루 및 신고·발견·악화·완화 전개를 제공한다. 테러 여부는 플레이어에게 즉시 확정 진실로 보여주는 정보가 아니다.
- [Hazards.cs](../../Assets/ChooGuard/App/Fps/Emergency/Hazards.cs)의 `Position`, `Where`, `Label`, `Active`, `Clearance`, `DangerRadius`, `Blocks`, `ApproachRadius`는 길 안내와 접근 통제의 공통 계약이다. 새 결과도 이 계약을 지켜야 한다.

수정 전에는 `Separate()`가 이미 발생한 `Kind` 전체를 막아, 다른 객체에서 같은 종류의 별개 원인을 판단하지 못했다. **이번 변경에서는 `composedOrigins`의 원자 원인 `Key` 단위로 중복을 막는다.** 따라서 객체별 키가 다른 두 가방의 소유자 이탈, 두 설비의 같은 종류 이상은 각각 후보가 될 수 있다. 같은 객체의 같은 원자 원인을 한 근무에서 반복 실행하지 않는 제약과 진행 중 사건에 새 지진을 중첩시키지 않는 제약은 유지했다. 이를 모든 원인이 무제한으로 동시 발생한다고 해석해서는 안 된다. 실제 자원 충돌, 객체 상태와 대응 부하는 계속 검사·판단해야 하며, 개수·시간 계산과 물리적 가능 여부는 코드가 맡는다.

매달린 객체도 이번 변경에서 한 ‘낙하물 사건’ 후보의 크기로 위치를 나중에 고르는 방식에서 벗어나, **실내에 실제 남아 있는 각각의 `HangingItem`을 원인으로 따로 판단**하도록 바뀌었다. 추첨 뒤에는 그 정확한 객체를 적용하고 실내 여부를 재확인한다. 이 변화 역시 코드 반영 확인이며 플레이 실행 성공을 뜻하지 않는다.

## 3. 객체 등록: Meshy 외형과 합성 능력을 분리한다

Meshy로 만든 모델을 놓는 것만으로 JEV가 그 객체를 원인으로 사용할 수 있지는 않다. 외형은 교체 가능하게 두고 다음 등록을 별도로 연결한다.

| 등록 항목 | 역할 | 예시와 주의점 |
|---|---|---|
| 식별·위치 | 원인이 어디의 어떤 객체인지 고정 | 배치 ID, 실내 공간 ID, 실제 위치, 활성 여부. 중복 ID·실외 객체는 합성 후보에서 제외한다. |
| 능력 태그 | 객체가 할 수 있는 변화를 선언 | `powered`, `contains_water`, `heated`, `suspended`, `portable`, `blocks_passage`, `sends_alert`, `supports_accessibility`. 태그만으로 사건을 자동 발생시키지 않는다. |
| 현재 상태 | 판단에 필요한 조건을 전달 | 전원 공급, 온도 상태, 물기, 고정 상태, 소유자 거리, 정상·고장·점검 상태, 마지막 확인 시각. 아직 구현하지 않은 값을 사실처럼 만들지 않는다. |
| 연결 | 연쇄가 실제 이웃·회로·공간을 따라가게 함 | 급전 설비→차단기, 누수원→젖는 표면, 감지기→수신기→셔터, 공조→연결 실내 공간, 통로→대체 통로. 연결이 없으면 그 연쇄 후보도 없다. |
| 센서·관찰 | 언제 누가 알 수 있는지 결정 | 시야·거리·소리·냄새·경보·수신 기록. 숨은 상태는 JEV의 세계 판단에 필요한 부분과 플레이어가 인지한 정보를 분리한다. |
| 물리·이동 | 원인과 피해가 허공에서 나타나지 않게 함 | 콜라이더, 바닥·벽 접촉, 낙하 범위, 통로 폭, 이동 가능 공간, 액체·연기 전달 경계. 장식 모델만 있으면 물리 원인으로 등록하지 않는다. |
| 원자 전이 공급자 | 해당 객체의 가능한 ‘다음 변화’를 생성 | 정상→과열, 고정→느슨함, 소유자 동반→소유자 이탈, 건조→젖음. ‘복합테러 시나리오 시작’ 같은 전이는 만들지 않는다. |
| 대응 상호작용 | 플레이어 조치가 세계에 영향을 줌 | 보고·통제·대피 안내·상태 확인, 기존 설비의 전원·밸브 조작. 새 조작은 게임 역할 검토와 실제 구현을 거쳐야 한다. |
| 종료·기록 | 원인과 결과, 인계를 추적 | 원인 객체 ID, 상태 버전, 평가 시각, 적용된 원자 변화, 파생 원인 ID, 발견 경로, 대응·인계 결과. |

기존 `StationEquipment`의 필드와 `Data`는 일부 메타데이터를 담을 수 있으나 범용 능력 태그·연결 그래프·원자 전이 공급자가 모두 구현되어 있다는 뜻은 아니다. 새 시스템은 객체 특성을 소유한 컴포넌트가 검증하고, 등록된 공급자에서 전이를 모으도록 확장하는 것이 적합하다. 모델 이름이나 자유 서술만으로 새 물리 법칙을 실행하지 않는다.

우선 등록할 입력 객체 묶음은 다음과 같다. 모두 ‘해당 게임맵에 배치·구현했을 때’라는 조건이다.

| 입력 객체 묶음 | 늘어나는 변화의 축 | 우선 연결할 능력 |
|---|---|---|
| 승객·동반자·수하물·유모차·휠체어 | 건강 양상, 소유자 이탈, 동반자 분리, 이동 제약 | 소유·동행 관계, 관찰 가능한 증상, 이동 지원 필요 상태 |
| 배터리·충전 단말·분전반·자판기·비상등 | 과열, 급전 이상, 국소 정전, 안내 실패 | 급전 그래프, 열·연기, 상태 확인·차단 연결 |
| 조리기기·가스 밸브·연결부·감지기 | 연기, 누출, 감지·자동 대응 성패 | 기존 주방·소방 연결 확장 |
| 실내 배수구·수도관·청소 카트·매트·바닥 | 누수, 유입, 미끄럼, 통로 축소 | 액체 전달·바닥 마찰·실내 경계 |
| 창·천장 패널·안내판·진열대·이동 칸막이 | 손상, 낙하, 전도, 시야·통로 방해 | 고정 상태, 접촉·낙하, 실제 차폐 범위 |
| 승강기·에스컬레이터·자동문·방화셔터 | 정지, 끼임, 우회·혼잡, 이동 약자 고립 | 기존 이동·끼임·통로 폐쇄 연결 |
| 실내 수신기·업무 전화·방송 단말·안내 전광판 | 확인·미확인 경보, 정보 지연·불일치 | 발신 근거, 메시지 상태, 영향 공간, 플레이어 인지 |
| 미확인 가방·밀봉 소포·분실물·누출 용기 | 소유자 확인, 접근 통제, 신고 연쇄 | 실재 물체·관찰 정보·인계. 공격 수단 구조는 등록 대상이 아니다. |
| 공조·실내 온도 센서·공기 상태 센서 | 더위, 공기 이상, 센서와 증상 불일치 | 연결 공간·유량·감지. 전파·환기 모델 구현 전에는 자동 확산 금지 |

## 4. JEV가 매번 다른 상황을 합성하는 흐름

공식 문서는 판단 하나를 범위가 좁은 원자 질문으로 만들고 그 결과를 코드에서 합성하는 방식을 설명한다. 상태와 구조화된 질문을 보내 구조화된 답을 받는 모델이므로, 세계의 실행 규칙과 연결은 게임 코드가 소유하는 구성이 적합하다. [TypeSafe Introduction](https://docs.typesafe.ai/introduction)

`Score` API는 정의한 순서 있는 단계에 대한 점수와 단계별 확률, 신뢰도를 반환한다. 이 확률을 CHOOGuard의 시간별 발생 위험률로 바꾸고 원자 변화를 실행하는 부분은 프로젝트의 합성 로직이며 API가 자동 제공하는 비상상황 시뮬레이터가 아니다. [TypeSafe API reference](https://docs.typesafe.ai/api)

1. **실재 객체 조회:** 활성 상태인 객체와 실내 위치를 확인한다. 승객·가방처럼 움직이는 객체는 현재 위치를 사용한다. 모든 후보를 열거하되 요청을 분할·순환해서 처리할 수 있다.
2. **가능한 원자 변화 생성:** 객체 공급자가 조건을 만족하는 변화만 낸다. 예를 들어 급전 없는 충전 단말의 급전 과열, 물 공급 없는 배관의 누수, 승객 없는 에스컬레이터의 승객 넘어짐은 후보가 아니다.
3. **필요 상태를 묶어 판단:** 후보마다 원인 객체·위치·현재 상태·인접 연결·관찰자·진행 중 위험과 대응 부하를 주고 JEV에 임박도와 변화 크기를 `Score`로 묻는다. 사건명이나 다음 대본을 자유 생성하라고 요청하지 않는다.
4. **게임 시간에 따라 적용:** 코드는 유효한 평가만 연속시간 위험률로 변환하고 디렉터 전용 난수열로 추첨한다. 추첨된 후보는 원인 객체, 실내 위치, 상태 버전, 연결 조건을 실행 직전 다시 확인한다. 오래된 응답이나 사라진 객체는 적용하지 않는다.
5. **변화 후 다시 판단:** 과열→연기, 물기→미끄럼, 정지→혼잡, 경보→신고, 안내→침착함, 차단→확대 가능성 감소처럼 바뀐 세계에서 새 원자 후보를 만든다. ‘반드시 화재→정전→테러’라는 다음 단계는 없다.
6. **개입이 분포를 바꿈:** 보고·통제·대피·설비 조치가 실제 상태를 바꾸고 JEV가 그 뒤의 임박도를 다시 평가한다. 악화 후보뿐 아니라 진정·감지·조기 신고·시설 담당 복구 같은 완화 후보도 갖춰야 한다.
7. **인지한 정보만 안내:** 길 표시와 HUD는 플레이어가 보고·듣고·보고받은 위험의 공통 API를 사용한다. 미발견 물체를 피하는 경로 모양만으로 숨은 사건을 누설해서는 안 된다. 시설 폐쇄는 플레이어가 인지한 상태를 따르되, 실제 충돌과 물리 장애물은 세계에 존재한다.

예를 들어 실제 `charging_terminal_12`가 급전 중이고 그 주위에 승객과 안내판이 있다면, `충전 단말 정상→과열` 후보가 성립할 수 있다. 적용 뒤 연기 발생 여부, 감지기의 감지, 승객의 발견·신고·접근, 연결 차단기의 상태, 안내판의 정보 전달, 해당 통로 혼잡을 각각 판단한다. 이 중 어느 변화가 먼저 일어나는지와 플레이어의 조치가 달라지므로 결과도 달라진다. 현장에 배관이 없으면 이 결과에 누수를 끼워 넣지 않는다.

## 6. ‘완전 랜덤’의 자유도를 늘리는 순서

첫째, 기존 원인이 실제 객체와 연결되는 정도를 높인다. 배터리·봉투·누수 후 젖는 전기설비처럼 일부 설명이 객체 특성을 가정하는 곳은 소유 객체와 연결을 등록한다. 이미 있는 설비와 승객을 재사용하면 다른 연쇄를 만들 수 있으며 새 외형의 개수보다 실제 상태·연결이 먼저 효과를 낸다.

둘째, 여러 분야가 공유하는 변화부터 추가한다. `젖음`, `과열`, `고정 약화`, `통로 축소`, `소유자 이탈`, `정보 수신`, `이동 지원 필요`, `주변 혼잡`, `악화/완화`는 다양한 객체와 결과에 재사용 가능하다. 구현은 각 변화의 물리·상태 계약을 검사한다. 범용 이름을 붙였다고 임의 모델에서 모두 사용할 수 있는 것은 아니다.

셋째, 별개의 객체에서 같은 원인이 나타나는 경우와 공통 원인이 여러 객체에 영향을 주는 경우를 구분한다. 두 가방의 소유자 이탈을 각각 판단할 수 있도록 이번 변경에서 원인 키별 중복 검사로 바꿨다. 한 회로 정전으로 여러 비상등이 영향을 받는 것은 별도의 사건 묶음이 아니라 실제 급전 연결을 확장할 후속 과제다. 서로 관련 없는 사건을 강제로 묶지 않는다. 대응 중인 인원·공간·기관 접근 같은 부하는 JEV의 임박도 판단 맥락에 포함한다.

넷째, 발견과 정보의 무작위성을 늘린다. 조기 목격, 늦은 감지, 신고 누락, 서로 다른 설명, 접근 가능한 통로, 동행자의 도움 요청이 대응 흐름을 바꾼다. 정보가 불완전한 상태를 표현하되 실제 위험의 정체를 HUD에 미리 공개하지 않는다. 실패만 무작위로 추가하지 말고 조기 신고·자연 진정·적절한 시설 차단도 합성한다.

다섯째, 전시·복합 보안 대응은 원자 능력이 갖춰진 다음 확장한다. 먼저 실내 확인 경보, 객체별 정보 상태, 동행 관계, 이동 약자 지원, 여러 통제 구역을 구현하면 시민 보호 관점의 복잡성이 생긴다. ‘전시 시나리오’나 ‘복합테러 시나리오’를 선택하는 새 상위 사건 메뉴는 필요하지 않다.

## 7. 확인해야 할 불변조건과 평가 항목

- 원인 객체를 삭제·비활성화하거나 실외로 이동하면 그 객체의 새 원인 후보가 사라진다. 적용 직전 이동·파괴에도 동일하다.
- 급전·물 공급·소유 관계·물리 연결을 끊으면 그 조건을 요구하는 후보와 파생 후보가 사라진다. JEV의 높은 평가도 불가능한 변화는 실행시키지 못한다.
- 새 외형만 등록한 장식 객체는 임의 원인을 생성하지 않는다. 해당 능력 공급자가 연결되어야 후보가 늘어난다.
- 다수 실내 층과 서로 다른 객체를 포괄하되, 특정 시드·시각·사건 순서를 기대값으로 두지 않는다. 같은 원인 여러 객체, 발견 지연, 악화·완화, 기관 인계, 입력 객체 제거의 경계 조건을 확인한다.
- JEV 부재·거부·응답 지연에는 새 합성을 로컬 가중치로 대체하지 않는다. 평가 만료·객체 변화 후 오래된 응답 적용을 막는다.
- 길 표시를 켜고 끄거나 HUD를 바꿔도 디렉터와 세계의 난수 소비가 바뀌지 않는다. 미인지 위험은 지도·경로·안내 문구로 누설하지 않는다.
- 개발용 기록은 원자 변화별 원인 객체·상태·JEV 평가·적용/취소 이유·인지 경로·플레이어 개입을 남긴다. 여러 근무의 원인 위치 분포, 원인 객체 다양성, 연쇄 깊이, 조기 발견/늦은 발견, 부하와 종료 가능성을 집계한다.
- Meshy 외형 품질, 객체 등록 검증, 원자 변화 구현, JEV 합성 실행, 실제 대응 적합성 검토는 서로 다른 완료 기준으로 보고한다. 이 문서의 제안은 실행 완료나 실제 현장 대응 검증을 뜻하지 않는다.
